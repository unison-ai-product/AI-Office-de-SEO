# AI Office de SEO キーワード・GSC・記事マップ要求 v3.7

> **権限移行注記（2026-08-03）**: 本書に残る`Owner / Admin / Editor / Viewer`は旧Role表現である。Keyword・Site戦略変更は`キーワード・サイト戦略`、分析設定変更は`サイト分析`、記事施策実行は`記事制作`の業務権限へ解決し、Site Assignmentと共通認可契約で判定する。

## 0. 市場とシェアの基本モデル

- Keyword Market: キーワードと同一SERP／intent clusterは、ユーザー需要の市場構造を表す。検索量、意図、ファネル、季節性、地域、AIO・広告面、競争性、traffic potential等は市場側の属性である。
- Observed Query Share: GSC Queryは、市場で実際に発生し対象Siteが表示・clickを得た需要の観測である。匿名化・切り捨て・未獲得需要があるため、GSC Query集合を市場全体とはみなさない。
- Article Share: 記事はcluster内のQuery群に対して順位、表示、click、CVを獲得する供給資産である。記事⇔Query⇔Keyword clusterの対応から、獲得、未獲得、分散、重複、保護、低下を評価する。
- 分離原則: `market_size/value` と `site_share/article_share` を別の値として保持する。市場が大きいことを自Siteが獲得できていることと解釈せず、現在シェアが小さいことだけを失敗とも解釈しない。
- シェア表現: 自SiteのGSC実測から算出する値は `observed_site_share`、競合順位・推定trafficから補う値は `estimated_search_share` と明記し、推定値を実測値として表示しない。

## 分類別正本への移行

動的Recommendationの判定正本は `logic/keyword-dynamic-recommendation-logic-requirements_v1.md` と `categories/logic-requirements_v1.md`、保持は `categories/data-requirements_v1.md`、GSC契約は `categories/integration-requirements_v1.md` を現在の正本とする。本書の `REQ-KGA-*` はキーワード・GSC・記事Mapの詳細要求として維持する。

## 1. 接続思想  ［REQ-KGA-01］

AI Office de SEOは、登録キーワード、GSCクエリ、記事URLを接続する。

```txt
Keyword Map
  ⇔ normalized keyword / same SERPs cluster
  ⇔ GSC query group
  ⇔ article canonical URL
```

リライト時は、キーワードパックと記事が実際に取得しているGSCクエリを比較し、SEOの軌道修正を行う。

## 2. キーワード正規化  ［REQ-KGA-02］

文字列正規化は候補化までとする。最終的に同一キーワードとして扱うかはSERPs集約で判定する。

正規化レイヤー:

- raw keyword
- lexical normalized keyword
- token reordered candidate
- alias candidate
- same SERPs cluster
- intent cluster

`ITエンジニア`、`it エンジニア`、`エンジニア it` のような表記ゆれは、まず候補化し、上位URL重複、PAA重複、AIO/AI検索面、GSC実績、検索意図の近さで同一扱いを判断する。

## 3. キーワードマップ自動生成  ［REQ-KGA-03］

ユーザーがメインキーワードを指定すると、候補キーワードを自動収集し、キーワードマップを生成する。

新規SiteのBootstrapでは、業界／業種、商品・サービス、対象顧客、地域、横断軸およびSite内容から、方向性を代表する**単一語のビッグキーワード候補**を先に生成する。候補はキーワードマップへ直ちに全件登録せず、ユーザーへ方向性確認として提示し、除外・追加を反映して探索起点を確定してから関連語、質問、類語、地域語等へ展開する。候補生成はLLMによる構造化推定とDataForSEO等の市場データ取得のいずれか一方へ固定せず、availability、費用、応答時間および検証可能性に応じて利用可能な経路を選択・併用できる。取得元が利用不能な場合も、利用可能な経路で継続し、根拠と取得可否を表示する。

Bootstrap候補は、(a) Site・商品・顧客情報からの抽出、(b) 業界／カテゴリからの探索、(c) ユーザー確認済みシード語からの展開、の3系統を区別する。複数系統で一致する候補は一致を根拠として保持するが、自動採用の十分条件にはしない。各候補は `discovery_sources[] / evidence[] / observed_at / provider_updated_at? / availability / confidence / user_feedback / analysis_version` を持ち、取得元の判定を事実として固定せず、SERP構成、Site適合およびユーザー修正で補正できる。

候補源（自動生成に加え、**ユーザーの手動追加を第一級の経路**とする。手動追加＝単発入力・一括貼り付け・CSVインポート・シード語からのサジェスト展開ビューでの選択登録。手動分も同一の正規化 `REQ-KGA-02`・分類 `REQ-KGA-04`・アサイン台帳照合 `REQ-KGA-14` のパイプラインを通す）:

- Google Autocomplete系
- 関連検索系
- Search Volume系
- Search Intent系
- PAA
- AIO / AI検索面観測
- 類語・関連語
- modifier
- entity
- 自サイトGSCクエリ

取得スコープ（ユーザー設定・対象サイト単位）: 候補収集は、設定画面「キーワード取得設定」（`REQ-NAV-04`）で対象サイトごとに指定した **検索エリア（全国／地域指定＝都道府県・市区町村を複数可）・デバイス視点（モバイル優先/デスクトップ/両方）・取得する語の種類（関連語/質問/類語/地域）** をパラメータとして反映する。地域指定はローカルSEO（商圏キーワード）を対象化するための取得フォーマット指定であり、内部データ源（DataForSEO）の location/device 指定へ写像する（源の名称は表示禁止語＝`REQ-NAV-01`）。地域キーワードは補助属性「地域性」（§13 判定材料）と接続する。未指定時の既定は 全国・モバイル優先・全種類ON。

## 4. キーワード分類  ［REQ-KGA-04］

各キーワードを以下に分類する。

- 必須キーワード: SERPs・競合上位5記事・GSC機会から見て主要論点に近いもの
- 推奨キーワード: FAQ、PAA、補足論点、本文補強に使うもの
- オリジナルキーワード: Domain PositioningやUser Orderから出る差別化語

キーワード詰め込みを禁止する。必須キーワードは自然挿入を前提とし、類語・言い換えもカバーとして認める。

## 5. カバー率  ［REQ-KGA-05］

記事ごとに、登録キーワードがGSC実流入クエリでどの程度カバーされているかを算出する。

- 登録キーワードカバー率
- クリック加重カバー率
- 未カバーキーワード
- ズレクエリ
- 想定外に成果が出ているクエリ

クリックが多いGSCクエリは、1記事につき1〜5程度の主要キーワードグループへマッチする前提で扱う。

## 6. Query Drift分類  ［REQ-KGA-06］

- intent_drift
- modifier_drift
- audience_drift
- article_type_drift
- brand_drift
- conversion_drift
- unexpected_success_query

Query Driftは、リライト原因解析とRepair Ticket発行に使う。

## 7. Article Map  ［REQ-KGA-07］

自サイト記事をURLベースでマップ化する。

保持するもの:

- canonical_url_hash
- title
- h1/h2/h3 summary
- article type
- target keyword groups
- observed GSC query groups
- keyword coverage
- content hash
- published / modified
- URL alias history

記事タイプ不一致、カニバリ、未カバーキーワード、リンク導線不足を判定する。

カニバリは、2記事以上の間で**キーワード被覆率の重複が50%を超え**、かつ対象クエリ群の**流入の30%以上が複数記事へ分散**しているケースを判定条件とする（初期しきい値、要調整）。判定はカバー率（`REQ-KGA-05`）とGSCのURL×クエリ実績から機械的に行い、検知したカニバリはアラートおよびリライト判断の入力とする。リライト・新規生成は、対象キーワードで既存記事をこのしきい値の側へ押し込まないことを制約とし、押し込む場合はサイト単位のキーワード割り当て見直しを促す。

## 8. データ保持・集約と判定ウィンドウ  ［REQ-KGA-08］

保持と集約:

- GSC Data Martの日次実績（site/page/query/page×queryの日次テーブル、`REQ-KGA-11`, `REQ-SEC-11`）とCV日次集計（`REQ-WPA-05`）は判定の正本として日次粒度で保持する。保持期間の初期値はGSC側の保持（約16か月）に揃え、要調整。憲章のデータ保有方針（GSC日次実績・CV日次集計の保持）と一致させる。
- 1週間のみ保持するのは、日次より細かいリアルタイム系データ（画面向けの細粒度スナップショット、進行中ジョブの中間集計等）に限る。
- 長期の参照・表示は月集約＋年集約をベースとし、日次正本から導出する。日次正本の保持期間を過ぎたデータは月次・年次集約のみ残す。

判定ウィンドウ:

- リライト候補判定は直近3か月のデータから行う。反映後は1か月後の一次評価、3か月後の二次評価、6か月後の長期評価を日次正本から算出する（`REQ-SEC-11`）。
- 判定が微妙な場合は、6か月の安定性など、より長い期間の傾向を確認する。
- しきい値・期間・保持期間は初期値であり、要調整。

判定主体:

- LLMによる判定は、原則としてエージェントシステム内（Research / Writing / QA / Repair 等のExecutor）に限定する。
- 一般システム（ダッシュボード、リライト候補抽出、カバー率・カニバリ・Query Drift判定、分散バッチ、集約）は、すべて機械（決定論的）判定で行い、LLMを使わない。

## 9. 内部リンクロジック  ［REQ-KGA-09］

内部リンクは、Google公式の具体ガイダンスをベースに機械的に候補選定する。出典:

- SEO Link Best Practices: https://developers.google.com/search/docs/crawling-indexing/links-crawlable
- Importance of link architecture: https://developers.google.com/search/blog/2008/10/importance-of-link-architecture

Google公式（そのまま要求化）:

- すべての重要記事は、他記事から最低1つの内部リンクを受ける（オーファン禁止）。
- アンカーは記述的・簡潔で、リンク元・リンク先の双方に関連させる。「詳細はこちら」等の汎用語を避け、文脈外で読んでも意味が通るかを確認する。
- リンクはクロール可能な `<a href>`、画像リンクは `alt` を使う。
- リンク先は「その記事の理解を助ける自サイトの関連資源」を文脈内で選ぶ。
- 重要記事はホーム/上位階層から到達可能にする。理想リンク数は定めず、多すぎると感じたら多いと判断する。
- リンク構造の人為的なテーマ分け（サイロ化）を目的にしない。トピック横断のリンクは妨げない。

候補選定ロジック（本製品、機械判定＝`REQ-KGA-08`）:

- Keyword Map、Article Summary、同一SERPs／intent cluster、GSC実績、現在の内部リンクから、記事×リンク先候補を集約バッチで算出する。記事本文を恒久保持したグラフDBを前提にしない。
- 成果/権威のあるページから対象ページへの流入リンク機会を提示する。
- 新規記事とリライト成果には、対象cluster、文脈、既存記事の役割に適合する既存記事へのリンクを生成工程で挿入できる。新規記事から既存記事へのリンクは利用可能な記事データから自動挿入し、QAでリンク先存在、文脈、anchor、重複、過多を検査する。
- 公開済み既存記事から新規・更新記事へリンクを追加できそうな場合は、対象記事、挿入文脈、anchor、リンク先、期待する接続をRecommendationとしてまとめる。対象Siteへの記事更新権限を確認し、ユーザー承認後に限定PatchまたはWordPress下書きとして実施する。公開済み記事を提案なしに一括更新しない。
- オーファン検知は独立した救済規則にせず、同じリンク元候補選定を使用する。適切なリンク元がなければ無理に接続せず、記事役割、cluster割当、統合・保留候補を提示する。
- アンカーは `internal_link_context` 由来で自然に生成し、過剰最適化は `injected_link_or_hidden`（`REQ-PACK-09`）で抑制する。1記事の主アンカーテーマを固定し、カニバリ（`REQ-KGA-07`）を抑える。
- QAは `internal_link_qa`、出力はWPの internal link slot / related article slot（`REQ-WPA-02`）へ接続する。
- 内部リンク削除は追加・編集と分離し、既存のリンク供給と回遊を減らすため自動実行しない。削除候補、影響、代替linkを提示してユーザー承認を必要とする。

第三者ヒューリスティック（公式ではない・要調整）:

- 目安として1,000語あたり2〜5本の文脈リンク、1ページの総リンクは過多を避ける、重要ページは3クリック以内、公開時に既存2〜3記事から流入リンクを付ける。

## 10. トピック網羅とグルーピング（内部管理）  ［REQ-KGA-10］

注意（正直な切り分け）: 「トピッククラスター/ピラー/トピカルオーソリティ/サイロ」はSEO業界の枠組みであり、Google公式の用語・保証された機構ではない。Googleはリンク構造の人為的サイロ化に利点を見出していない。一方、Google公式が支持するのは、トピックの包括的網羅（helpful content。語数ではなく網羅・深さ）、明快でクロール可能なサイト構造、関連コンテンツ間の内部リンク、断片化・オーファンの回避である。

本製品の扱い（ランキング機構としてではなく内部管理データとして）:

- Keyword Map（同一SERPs/intentクラスタ）とArticle Mapから、トピックのグルーピング（主題ハブと関連記事）を導出する。用途は次の3つに限定する。
  - 網羅とギャップ把握（`REQ-PACK-09` comprehensiveness と接続）。
  - キーワード配分（1記事1主トピックでカニバリを抑制、`REQ-KGA-07`）。
  - 内部リンク候補の生成（`REQ-KGA-09`）。
- グループ内の未カバー主題を網羅率として指標化する。
- 記事間のトピック重複が過度な場合は、統合または差別化を促す（カニバリ、`REQ-KGA-07`）。
- WordPress等の既存カテゴリ、階層、URL、slugを外部正本として読み取り、現在構造へ記事の役割とKeyword clusterを割り当てる。本製品はカテゴリ作成、所属変更、slug変更、301 redirect、canonical変更を自動実行しない。より適切な構造案は戦略レポートとして提示できるが、記事制作・内部リンクWorkflowからサイト構造を書き換えない。
- グルーピングは機械判定（`REQ-KGA-08`）で導出し、「ピラー/オーソリティ」等の業界用語はユーザー向けUIには出さない。

## 11. GSCデータ取り込みとフィルター設計  ［REQ-KGA-11］

GSCは固有の上限・匿名化・集計差異を持つため、無設計に全次元を取得すると量が破綻し、かつ誤分析になる。取り込みは以下を前提に設計する。出典:

- Performance data deep dive（フィルタと上限）: https://developers.google.com/search/blog/2022/10/performance-data-deep-dive
- Getting your performance data / Usage limits: https://developers.google.com/webmaster-tools/v1/how-tos/all-your-data , https://developers.google.com/webmaster-tools/limits

### 11.1 GSC固有の制約（前提）

- 行数上限: Search Analytics APIは1日・1プロパティ・1検索タイプあたり最大5万行（クリック降順の上位）。1リクエスト最大25,000行、`startRow`でページング。大規模サイトはロングテールが切り捨てられる。
- 匿名化クエリ: 数十ユーザー未満のクエリはクエリ次元から省かれ、クエリ行の合計は全体合計に一致しない（匿名化分は合計側にのみ含まれる）。
- 集計差異: page×query同時付与は最も高コストで欠損も生じる。正確な合計はpage/query次元を外して取得する（`aggregationType`に留意）。
- 保持と遅延: GSC側は約16か月保持。データは約2〜3日遅れ。
- クォータ: load quota（短期/長期）とQPS/QPM/QPDがあり、page/query groupingや広い日付範囲ほど高コスト。

### 11.2 取り込みフィルター設計（要求）

- 増分・日次取得: 1日分ずつ取得してData Martに蓄積し（公式推奨）、直近数日は遅延・改定に備え再取得する。全期間一括取得をしない。
- 速報値と確定値: Search Analytics APIの`dataState=all/hourly_all`で得る不完全データと、`final`の確定データを状態分離し、`first_incomplete_date`または`first_incomplete_hour`以降を速報として保持する。速報値は監視と早期通知には使えるが、施策評価、学習、月次配分の確定根拠には単独使用せず、確定値への置換後に再判定する。
- 次元スコープ: 用途別に次元を絞る。正確な合計はdate(+必要ならcountry/device)、URL×クエリは日次でページング（上位5万/日の切り捨てを許容）。全次元総当たりをしない。
- 優先度: 5万/日の制約下で、`REQ-SRC`のバッチ優先度（P0急増未登録クエリ〜P5低優先）に沿って重要URL/クエリを優先取得する。長尾欠損はサイト規模に応じ許容またはスケール手段へ回す。
- 負荷・クォータ管理: 不要なpage/query groupingと広い日付範囲を避け、QPS/QPM/QPD・load quota内に収め、quota超過はバックオフ・再試行する。夜間バッチで実行し、画面表示時に走らせない（`REQ-SEC-06`）。
- グローバル配分: GSC取得は`REQ-SRC-07`のグローバルレート/クォータ配分とスタッガリングに従い、テナント横断で共有されるper-projectクォータを尊重する（テナント個別が上限内でも合算で超えないようにする）。
- スケール手段: 大規模サイトはGSC Bulk Export（BigQuery。行数上限なし・非遡及。匿名化クエリは**メトリクス行として含まれる**——`is_anonymized_query=true`でクエリ文字列はnull/空文字列。クエリ文字列自体は取得できないため、匿名化行を通常クエリと同列に扱わず、集計の完全性確保と匿名化シェアの計測に用いる）を選択肢にする。またはディレクトリ別サブプロパティで5万/日枠を分割する。中小サイトはAPIで足りる。
- Bulk Exportの費用制御: BigQuery生テーブルを画面から都度集計せず、日次の必要粒度へ事前集約して表示・判定に使用する。直近詳細と長期集約を分離し、保持期間、partition、scan上限および大規模Site・上位プランでの提供条件を設定管理する。
- 検索タイプ: 主にwebを取得し、image/videoは必要時のみ（5万枠は検索タイプ別）。AIO/AI Mode由来はwebに混合され分離フィルターはない。
- Generative AIレポート（Beta）: ページ単位インプレッションのみ・クエリ次元なし・段階提供。取得可否はavailabilityとして扱い、`source.gsc.ai_report.v1`（`REQ-KGA-17`）へ供給する。
- サイト境界とメタデータ: 取得は`tenant_id`/`site_id`スコープで行い、匿名化・切り捨て・取得次元・データ日をメタデータとして記録する（`REQ-SEC-02`）。GSCデータは都度API参照ではなくData Martへ（`REQ-PRODUCT-05`）。

### 11.3 分析への含意

- カバー率（`REQ-KGA-05`）、カニバリ（`REQ-KGA-07`）、Query Drift（`REQ-KGA-06`）は、「クエリ行合計＜総合計（匿名化分）」と「上位5万/日の切り捨て」を織り込んで算出し、欠損を明示する。匿名化・切り捨てで見えないクエリを「流入ゼロ」と誤判定しない。
- 判定は機械（一般システム、`REQ-KGA-08`）で行い、取得しきい値・次元・優先度は初期値であり、サイト規模に応じてL3で較正する。

## 12. Keyword Map Graph と契約強化  ［REQ-KGA-12］

（正本: 旧 contract-hardening / keyword-map-competitor-article-map-batch を移植）

- Keyword Map Bootstrap: DataForSEOから正規化・SERPs集約でキーワードマップを構築し、`keyword ⇔ GSC query ⇔ 記事URL` をグラフとして接続する（`REQ-KGA-01`）。
- SERPs集約閾値: 同一SERPs判定・intentクラスタ化のしきい値を持つ（初期値・要調整、`REQ-KGA-07`）。
- Eligible Competitor Top5: 競合上位5記事はEligible Selection（記事タイプ・ロケール・除外条件）で選び、本文全文は保存せず構造を抽象化する（`REQ-SRC-03`）。
- Keyword Classification Evidence: キーワード分類（必須/推奨/オリジナル、intent）に証跡を残す。
- Keyword Stuffing Guard: 過剰SEO・同一語反復を機械判定でガードする（`REQ-PACK-09` keyword_stuffing、`REQ-PACK-10`）。
- GSCデータ状態と Query Drift分類: index_pending・匿名化・切り捨てを状態として持ち（`REQ-KGA-11`）、Query Driftを分類する（`REQ-KGA-06`）。しきい値は初期値でL3較正。

## 13. 決定論的キーワード属性とターゲット/業界軸フィルター  ［REQ-KGA-13］

キーワード戦略の絞り込み・見直しを、LLMを使わず（`REQ-KGA-08`）、既に取得済みのデータと辞書・ルールで機械化する。判定材料はすべて既存の取得物を再利用し、追加の外部取得・LLM費用を発生させない。

属性の付与（正規化キーワード／同一SERPsクラスタ単位）:

- intent型: Know / Do / Website / Visit（`REQ-AGENT-08`のNeeds Met分類に整合）＋商用性フラグ（比較・おすすめ・ランキング等のmodifier由来）。
- ファネル・事業適合: 認知、比較検討、意思決定、既存顧客支援等の段階と、商品・サービス、顧客、CV地点との適合を付す。直接CVだけでなく、Siteとして必要な情報充足も別成分として保持する。
- ターゲット適合: キーワードのmodifier・共起語を、サイトの `target_axes[{segment, literacy, situation}]`（`REQ-PRODUCT-12`）と辞書照合し、segment/literacy/situation別に in-target / out-of-target / unknown を付す（例: 「未経験」「初心者」→literacy低・状況=入門、「年収」「転職」→situation=転職検討）。
- 業界・トピック適合: entity×業界タクソノミ×Domain Positioning の照合で in-domain / adjacent / out-of-domain を付す。Fanout（`REQ-SRC-02`/`REQ-SRC-09`）由来の域外候補ノイズを自動降格する。
- YMYL近接: `catalog.quality_gate.ymyl_bar` の分類辞書でフラグし、生成時の基準引き上げ（`REQ-PACK-09`）へ接続する。
- 競争・実現性: 検索需要、競合強度、上位サイト傾向、Siteのトピック信用適合、既存記事との重複・カニバリ、AIO・広告・SERP機能による市場圧力を保持する。詳細な価値計算は`REQ-KGA-17`を正本とする。
- 補助属性: 地域性、ブランド／非ブランド、季節性、鮮度要求、想定記事タイプ、既存記事への割当状態。季節性は検索ボリュームとGSC表示回数の時系列から判定し、短期変動を恒常需要として扱わない。

季節性の初期データ源はDataForSEO等の月次検索量履歴とGSC表示回数とする。Google Trends API等はProvider Adapter経由の後続補助入力として追加可能にし、特定Providerを必須化しない。補助入力が未提供、限定公開または取得不能の場合は`unknown`として初期判定を継続し、取得可能になった時点で対象clusterだけを再計算する。

判定材料（すべて決定論・既存取得物の再利用）:

- modifier辞書・entity辞書・業界タクソノミ: Catalogとして版固定し、編集は`REQ-ADM-10`（Pack・プロンプト・ゲート管理）、重み・しきい値は設定レジストリ（`REQ-ADM-09`）。辞書は初期値・要調整のヒューリスティックであり、順位保証ではない。
- SERP構成: 上位結果タイプ・競合記事タイプ分布（`REQ-SRC-03`のCompetitor Structure、`REQ-SRC-06`キャッシュを再利用）。
- PAA・自サイトGSCクエリ共起。

フィルターとビュー（`REQ-NAV-04`のターゲットフィルター・リテラシーフィルターの実体定義）:

- ターゲット外・リテラシー不一致・業界外キーワードの除外候補提示（自動削除ではなく降格＋提示。採用/却下は`recommendation_feedback`へ）。
- ギャップマトリクス: ターゲット軸×intentの2軸で、登録済み・記事あり・未カバーの象限を提示し、トピック網羅（`REQ-KGA-10`）と新規記事候補へ接続する。
- 属性は `source.keyword.map.v1` のJSONに `attributes` として追補する（`REQ-PACK-07`）。

## 14. キーワード⇔記事アサインメント台帳（連携の確実化）  ［REQ-KGA-14］

keyword⇔GSCクエリ⇔記事のグラフ（`REQ-KGA-01`/`REQ-KGA-12`）に、事後検知（カニバリ、`REQ-KGA-07`）だけでなく事前規律を与える台帳を持つ。

台帳:

- 必須/推奨キーワードグループ（`REQ-KGA-04`）ごとに、主担当記事を高々1つ割り当てる（1記事1主トピック、`REQ-KGA-10`の実行形）。状態: unassigned（バックログ）/ planned / assigned / retired。
- 記事側は内部ID・canonical_url_hashで同定し、URL変更・エイリアスでも割り当てが追従する（`REQ-PRODUCT-03`）。
- 記事⇔キーワードの主従構造（プライマリ/セカンダリ）: 各記事は**主対策キーワード（プライマリ）を高々1つ**持つ（タイトル/H1で狙う軸＝主担当キーワードグループの代表語）。加えて同記事が自然に内包する**従キーワード（セカンダリ）を複数**持てる（関連語・ロングテール・PAA・言い換え由来＝`REQ-KGA-04`の推奨/オリジナル）。プライマリは「1グループ1主担当記事」（上記）と一致し、セカンダリはグループ内の被覆語として重複可だが、**他記事のプライマリと同一グループになる場合は二重アサインとしてアラート**（上記整合保証）。プライマリ/セカンダリは生成・リライトのブリーフ（`REQ-RWR-08`）・キーワードマッピングUI・カバー率判定（`REQ-KGA-05`）に引き継ぐ。UI表示語は「メインキーワード／サブキーワード」等の一般語（`§6.5`対訳表・`REQ-NAV-09`）。

整合保証（決定論・バッチ/イベント時検査、`REQ-KGA-08`）:

- オーファンキーワード（担当記事の削除・retire）、オーファン記事（主担当キーワードなし）、二重アサイン（同一グループへ複数記事）を検出し、ハードロックではなくアラートで提示する（`REQ-PRODUCT-03`の思想、通知は`REQ-PRODUCT-11`）。
- 生成・リライトのIntake Gate（`REQ-AGENT-09`）で台帳を決定論プレチェックする: 対象キーワードグループが他記事にassigned済みの場合、**LLM実行・クレジット消費の前に**警告し、リライト誘導またはキーワード割り当て見直しを提案する。`REQ-KGA-07`「しきい値へ押し込まない」制約の事前形であり、無駄なLLM費用の発生自体を防ぐ。

Query Driftとの循環（すべて機械判定）:

- unexpected_success_query → 推奨キーワードへの昇格候補または新規記事候補として提示。
- intent_drift / article_type_drift → アサイン見直し提案（担当替え・分割・統合）。

Source Pack: `source.keyword.assignment.v1` を追加する（`REQ-PACK-07`。`{article_ref, primary_keyword_group, secondary_keyword_groups[], state}` を含み、プライマリ/セカンダリの主従を運ぶ）。しきい値・辞書は初期値・要調整。

## 15. GSCクエリ⇔キーワードマップの決定論的マッチングカスケード  ［REQ-KGA-15］

背景（プロトタイプの既知課題）: 記事が実際に獲得するGSCクエリと登録キーワードマップのマッチ率が低い。原因は (a) 字面中心のマッチングが日本語ロングテール（語順・助詞・表記ゆれ・修飾語付加）を取りこぼす、(b) 全GSCクエリへのSERPs集約検証はクォータ・費用的に不可能（`REQ-KGA-11`の行数上限、`REQ-SRC-06`予算）、(c) 匿名化クエリは構造的にマッチ不能。対策はLLMを使わず（`REQ-KGA-08`）、以下の多段決定論カスケードで行う。

カスケード（上段から確定。判定方法・しきい値は初期値・要調整）:

1. exact: 正規化形での一致（`REQ-KGA-02`のlexical / token reordered）。日本語は形態素分割・全半角・かな漢字表記ゆれ・助詞除去を正規化に含める（決定論の形態素解析を用いる。実装選定はL3、LLMは使わない）。
2. synonym: 類語・エイリアス辞書（`source.keyword.synonym_related.v1`。辞書はCatalog版固定・`REQ-ADM-10`編集）で展開したトークン集合の一致。
3. containment: 登録キーワードグループの中核トークンをGSCクエリが包含する場合、同グループへ帰属し、余剰modifier（例: 「30代」「未経験」）を属性・サブ意図候補（`REQ-KGA-13`）として記録する。日本語ロングテールの主要な受け皿。
4. co-landing: **GSCのURL×クエリ実績そのものを証拠に使う。** あるクエリが、既にグループGへマッチ済みのクエリ群と同一URLへ着地しており、トークン重なりがしきい値以上なら、Gへ帰属する（自前データのみ・外部費用ゼロ）。co-landingで安定した対はエイリアス候補として`REQ-KGA-02`のalias層へ還流し、辞書を機械的に育てる（マッチ率が運用で上がる自己改善ループ）。さらにk匿名しきい値を満たした対はグローバル辞書候補へ昇格提案し、全テナントのマッチ率を底上げする（`REQ-PRODUCT-13`）。
5. serp-verified: ここまで未解決かつ高クリックのクエリに限り、予算・キャッシュ配下（`REQ-SRC-06`）でSERPs集約検証を行う。優先度は`REQ-SRC-05`のP0（急増未登録クエリ）と同一機構。**全クエリのSERP検証はしない。**
6. unmatched: 解決しないクエリは未マッチとして明示保持し、どこかへ強制的に寄せない。高クリックの未マッチは新規キーワード候補（`REQ-KGA-06` unexpected_success_query）・アサイン台帳のバックログ（`REQ-KGA-14`）へ提示する。

信頼度と計測:

- 各マッチに method（exact / synonym / containment / co_landing / serp_verified）と confidence を記録し、`source.gsc.query_group.v1` の出力に含める（`REQ-PACK-07`）。
- マッチ率KPIは**クリック加重**で定義する（クエリ本数加重はロングテール構造で低く出るため主KPIにしない）。分母は可視クエリに限り、匿名化分（クエリ行合計＜総合計、`REQ-KGA-11`）は構造的上限として別掲する。100%は原理的に到達不能であることを明示し、誤った目標設定を避ける。
- カバー率（`REQ-KGA-05`）・Query Drift（`REQ-KGA-06`）・カニバリ（`REQ-KGA-07`）はマッチ信頼度を織り込み、低信頼マッチのみを根拠に重大判定（リライト・統合）を確定しない。
- マッチ率と段別内訳は、検索流入分析（ユーザー画面）と観測ダッシュボード（`REQ-ADM-04`）で監視し、辞書・しきい値の較正（`REQ-ADM-09` / `REQ-ADM-10`）の入力にする。

処理位置: マッチングは夜間バッチの事前計算（`REQ-SRC-05`）で行い、画面は事前計算結果の配信とする（`REQ-SEC-06`）。

## 16. ロングテールの集約と昇格（GSC→キーワードマップ還流）  ［REQ-KGA-16］

`REQ-KGA-15`の未マッチクエリ昇格は高クリック条件であり、単体では低クリックのロングテールが漏れる。裾は単クエリでなくクラスタ集計で評価し、キーワードマップへ還流する。すべて機械判定（`REQ-KGA-08`）。

- 集約: 未マッチクエリおよびcontainmentマッチの余剰modifier群を、共有中核トークン・modifierパターン・co-landing先URLの一致で決定論クラスタリングし、クラスタ単位でクリック・インプレッションを集計する。
- 昇格条件: **クラスタ集計値**のしきい値（単クエリのクリックしきい値ではない）。急増（P0、`REQ-SRC-05`）とは別に、定常ロングテールを低優先の定期バッチ枠で評価する（優先度・しきい値は初期値・要調整、`REQ-ADM-09`）。
- 昇格先の2形態:
  - (a) 親グループあり: 既存キーワードグループのmodifier拡張（サブ意図）として登録し、アサイン台帳（`REQ-KGA-14`）の担当記事に対するセクション追補・FAQ候補（faq_answer等の意味ユニット、PAA接続）としてリライト候補の入力へ接続する。
  - (b) 親なし: 新規グループとしてバックログ（unassigned）へ登録し、ギャップマトリクス（`REQ-KGA-13`）と新規記事候補へ提示する。
- 構造的限界の明示: 匿名化しきい値未満のクエリは原理的に取得できない（`REQ-KGA-11`）。不可視の裾に対しては、PAA・オートコンプリート・類語・Fanout（`REQ-KGA-03` / `REQ-SRC-09`）を代理候補源として位置づける。API上位5万行/日の切り捨てが効く大規模サイトはBulk Export（`REQ-KGA-11`）でロングテール行を回収する。
- 品質ガード: 昇格はキーワード詰め込みの根拠にしない。記事側への反映は自然挿入・類語被覆の原則（`REQ-KGA-04`）とQuality Gate（`REQ-PACK-09` keyword_stuffing）配下で行う。

## 17. キーワード価値スコア（市場圧力を織り込む実効価値）  ［REQ-KGA-17］

需要量（検索ボリューム・インプレッション）だけでは、実際に獲得できる価値を判断できない。市場側の主要な影響を **AIO、リスティング広告占有、ドメイン信用性との適合・乖離** の3軸として観測し、キーワードグループ/クラスタにクリック・信頼獲得・CVとして実現しうる価値を決定論で付与する。

スコアのコンポーネント（重み・式はレジストリ管理・初期値要調整、`REQ-ADM-09`）:

- demand: 自サイトGSCインプレッション、検索ボリューム（DataForSEO、`REQ-SRC-06`キャッシュ）。
- realizable_ctr（実現可能CTR係数）: 自サイトの順位別期待CTR基線（**自データから**device・intent別に導出）に対する実CTR残差で補正する。自サイトデータが不足する新規サイトは、テナント横断のセグメント別prior（`REQ-PRODUCT-13`）から開始し、蓄積に応じて自サイト実測へ縮小推定で移行する。AIO観測あり（`source.serp.aio.v1`）のクエリ群に系統的な負残差が確認された場合のみ、そのサイト・意図での実測割引として適用する。**固定のAIO低下率を仮定しない**（外部研究は幅が大きく、自サイト残差で較正する）。AIO観測が取得不可（availability欠損）の場合は割引を適用せずunknownとし、捏造しない（`REQ-WPA-10`の原則）。
- aio_pressure: AIO表示率、AIO内被引用、AIO観測群のCTR残差から、ゼロクリック化と被引用機会を分けて持つ。AIO表示は一律の負要因にせず、引用獲得を狙う戦略価値も別成分にする。
- paid_pressure: リスティング広告の本数、上部占有、ショッピング/ローカル等の有料・高占有面を観測し、自然検索結果へ到達する前のクリック競争を表す。広告主・入札価格を推測せず、観測可能な面構成だけを使う。
- domain_credibility_fit: 対象トピックに対する自サイトの信用成立度を、既存記事被覆、関連クエリ実績、指名・ブランドクエリ、トピック内の順位実績、ArticleSummaryの根拠・著者・更新状態、外部リンク等の取得可能な信号から評価する。一般化された単一の「ドメインパワー」を事実として扱わず、**トピック単位の相対的な適合・信用ギャップ**として表す。データ不足はunknownとする。
- serp_features: 広告以外のSERP構成（強調表示・動画・ローカル等のresultタイプ分布、`source.serp.result.v1`）によるクリック分配の補正（ヒューリスティック・要調整）。
- intent・商用性・CV近接: `REQ-KGA-13`属性。CVは相関ベースの補助として扱い、因果を主張しない（`REQ-WPA-05`の位置づけを維持）。
- fit乗数: ターゲット適合・業界適合（`REQ-KGA-13`）。

出力と接続:

- `keyword_value_score` と市場圧力3軸をグループ/クラスタへ付与し、ギャップマトリクス、新規記事候補、リライト優先度、ロングテール昇格判定へ接続する。`source.keyword.map.v1` のattributesに `value_score` / `aio_pressure` / `paid_pressure` / `domain_credibility_fit` / `market_pressure_availability` を含める（`REQ-PACK-07`）。
- AIO抑制と判定された群には、戦略の見直しを機械的に提示する: 期待クリック割引の可視化、AIO内被引用の観測（best-effort）、同意図でAIO影響の小さい変種・商用寄り変種への配分見直し。
- 本スコアは優先度付けの内部指標であり、順位・流入の保証ではない（`REQ-PACK-10`と同型の位置づけ）。判定はすべて一般システムの機械判定（`REQ-KGA-08`）。

計測上の交絡（Google公式仕様に基づく前提。検証ログ参照）:

- GSCはAIO/AI Mode由来のクリック・インプレッションをweb検索タイプへ混合して計上し、**クエリ単位で分離するフィルターを提供しない**。したがって、クエリ別のAIO表示判定フラグはGSCからは得られず、SERP観測（`source.serp.aio.v1`）由来とする。残差法が検出するのは「AIO込みの実測CTR」の系統的偏差である。
- AIOは1ブロック＝1ポジションで全リンクが同一positionになり、同一URLがAIOと通常結果の両方に出ても1インプレッションに重複排除される。position別期待CTR基線の導出時、AIO表示観測クエリ群のposition意味論が通常と異なることを織り込む。
- AI由来の計上方法は2025年に変更されており、基線導出は計上方法変更後のウィンドウを用い、方法変更由来の不連続を較正時に検出・除外する。
- Search ConsoleのGenerative AIレポート（Beta・段階提供）は**インプレッションのみ**（ページ・国・デバイス・日付次元。クリック・CTR・position・クエリなし）であり、CTR算出には使えないが、「AIO/AI Mode内で被引用されているページ」の公式観測として `source.gsc.ai_report.v1` で取り込み、被引用観測（本節のAIO内被引用）をSERPスクレイピング単独からページ単位の公式データで補強する。提供状況に依存するためavailability付きで扱い、未提供時は捏造しない。

## 18. トピック起点の多元化とSERP面適応（keyword / news / video）  ［REQ-KGA-18］

記事コンテンツは、トピックの発生源とSERP面構成で変わる。既存のSource Pack（`source.news.google.v1` / `source.youtube.search.v1`、`REQ-PACK-07`。取得はDataForSEO既存要求`REQ-SRC-01`の範囲内で新規外部依存なし）を、戦略層と生成ワークフローへ配線する。

起点3類型（候補はアサイン台帳バックログ`REQ-KGA-14`へ起点タグ付きで還流し、価値スコア`REQ-KGA-17`で優先度づけ。判定材料はすべて決定論`REQ-KGA-08`）。**どの情報ソース候補からコンテンツを作るかの採用判断はユーザーが行う**——システムの役割は候補提示までであり、自動採用はfull_auto/Autopilot許可レベル（`REQ-WPA-04`）の範囲に限る。作成フロー（コンテンツ作成画面）に起点の選択を置く:

- keyword起点（既定・既存）: キーワードマップ由来（`REQ-KGA-03`）。
- news_trend起点: Googleニュース観測（短TTL・予算・availability配下`REQ-SRC-06`/`REQ-SRC-07`）から、自サイトの業界適合（`REQ-KGA-13`）を満たす時事トピック候補を定期抽出する。時事性が高いためバックログ滞留ではなく鮮度期限つき候補として提示する。
- video_demand起点: SERPのvideo面比率（`REQ-KGA-13`の面構成属性）＋GSC video検索タイプ（`REQ-KGA-11`のオプション）＋YouTube検索観測から、動画需要の強いトピックを検知する。

記事タイプ決定への配線（Research & Outline）:

- `REQ-PACK-08`のResearch & OutlineステージのSource Needに、SERP面構成と、起点に応じた `source.news.google.v1` / `source.youtube.search.v1` を含める。
- 決定ルール（エージェントがカタログ制約内で決定、`REQ-PACK-11.1`）: news支配SERPまたはnews_trend起点→`news_column`を優先し`freshness_honesty`ゲート（`REQ-PACK-09`）を必須化。video支配SERP→`video_reference`意味ユニットを推奨し、結論先出し（`summary_tldr`）先行の構成を優先。News/YouTube由来コンテンツは常にcontent_role分離のデータ扱い（`REQ-AGENT-07`）で、本文へ丸写ししない。

鮮度と実行レーンの整合（`REQ-BILL-11`）:

- 鮮度要求highのジョブ（news_trend起点・news_column型）は interactive/優先実行を既定とし、scheduled（夜間バッチ）選択時は鮮度低下の注意を表示する。鮮度シグナルはレーン既定の決定入力とする。

意味ユニット追加: `catalog.purpose_element.*` に `video_reference`（動画参照・埋め込み文脈。埋め込み可否はWP Capability `REQ-WPA-08` 配下）を追加する（列挙は拡張可能・初期集合の規約内）。しきい値（面比率・news_trend評価周期・鮮度期限）は初期値・要調整（`REQ-ADM-09`）。

## 19. サイトトポロジー戦略（幹→枝→葉・カテゴリ×タグの網目）  ［REQ-KGA-19］

キーワードクラスタを記事の**階層トポロジー**として計画し、内部リンク網を計画的に構築・維持する。

- 階層モデル: キーワードの検索規模・語数・intentから、幹（ピラー=大きなキーワードを支えるコア記事）→枝（クラスタ記事）→葉（ロングテール/FAQ）の階層を割り当てる（決定論、`REQ-KGA-08`。割当規則の重みは`REQ-ADM-09`）。強化カテゴリーとコア記事はユーザーが指定できる（採用判断はユーザー、`REQ-KGA-18`と同原則）。
- 縦リンク（ツリー）: 幹⇔枝⇔葉の双方向リンクを基本構造とする。横リンク（網目）: 軸は違うが話題が近いトピッククラスタ（`REQ-KGA-10`）にタグを割り当て、タグ経由の横断リンクを差し込み、カテゴリー×タグが網目になるリンク網を作る。WPのカテゴリー/タグ（タクソノミ、`REQ-WPA-08`のCapability配下）へ写像する。
- 生成順序: ユーザー行動の順でCVに近いカテゴリ/トピックから生成する既定順（価値スコアのCV近接、`REQ-KGA-17`/`REQ-KGA-13`）。コア記事を中心に外堀を埋める順序をトポロジープランナーで提示し、採否はユーザー。
- リンク再調整ループ: 記事の追加・公開・削除のたびに、親（枝→幹）・兄弟・タグ横断の**リンク再調整候補を都度生成**し、承認制の小リライトとして適用する（`REQ-KGA-09`の候補選定・オーファン禁止に接続。葉を作ったら枝を強化、枝を作ったら幹を強化）。
- 制約: リンクは自然な文脈内挿入を原則とし、詰め込み・過剰リンクはQuality Gate配下（`REQ-PACK-09`）。

## 20. ウォッチリストと変動監視（急変・アルゴ・季節）  ［REQ-KGA-20］

- キーワードウォッチリスト: 上位を取りたい・価値の高いキーワードをユーザーが**手動でピン留め**し、順位・クリック・SERP構成の変化をしきい値つきで監視・通知する（`REQ-PRODUCT-11`）。継続下落はリライト候補（`REQ-RWR-06`）・内部リンク強化（`REQ-KGA-19`）・CTA見直し（`REQ-PACK-17`）への導線を提示する。
- サイトレベル急変検知: トラフィック・CV・追跡キーワード順位の日次急変を決定論で検知し（変化率しきい値・要調整）、要因分解ビュー（対象ページ/クエリ群・SERP構成変化・インデックス状態）を提示する。
- SERP変動・アルゴリズム更新: 自サイト追跡キーワード群のSERP変動度を自前データから集計する（外部固定指標に依存しない）。Google公式のランキング更新・ステータス情報は情報ソースとして取り込み（availability・取得経路はL3確認、検証ログ）、**変動期間中はリライト・統合の重大判定を保留する判断ガード**を提示する（慌てて触らない、の実務知恵を機械化。`REQ-KGA-15`の低信頼時ガードと同型）。
- 季節変動: GSC日次実績16か月保持（`REQ-KGA-08`はこの用途のための設計）を用いたYoY比較で季節パターンを検知し、**シーズン前に**該当記事のリフレッシュ（最新情報更新・バナー/CTA差し替え=リライトoperation）候補を提案する（提案→ユーザー採否）。

## 21. インデックス状況・技術ヘルス監視  ［REQ-KGA-21］

- インデックス監視: 公開済みURLのインデックス登録状況をGSC／URL Inspectionで確認し（URL検査系APIのクォータ配下・優先度順=新規公開/順位なし/ウォッチ対象から。クォータ実数はL3確認・検証ログ）、未登録・除外・エラーを問題一覧として提示する。index_pending（`REQ-KGA-11`）と統合表示する。
- 技術チェック（決定論）: 取得済みページからcanonical・robots・構造化マークアップ・リンク切れを機械検査し、原因候補とユーザー確認事項を提示する。本製品は記事を制作・更新するがサイト構築・サイト全体設定を責務としないため、自動修復せずユーザーエスカレーションへ接続する。権限者は `未確認／確認済み／外部対応中／解消` を更新でき、解消後はGSCで再検証する。判定にLLMを使わない（`REQ-KGA-08`）。

## 22. ローカルSEO（地域検索最適化）  ［REQ-KGA-22］

地域の店舗・サービス事業者向けに、ローカル検索（Local Pack＝地図＋3枠・「近くの」/地域修飾クエリ）での可視性を、**コンテンツSEOの範囲で**最適化する。地域スコープ設定（`REQ-KGA-03`の取得スコープ・全国/地域指定）を起点とし、対象サイト単位で有効化する。Googleビジネスプロフィール（GBP）自体の運用代行・レビュー収集・GBP投稿は本製品の主機能ではない（out of scope）が、①ローカル順位の観測、②ローカル向けコンテンツ（地域ページ）の生成、③技術シグナル（構造化データ・NAP整合）、④ローカル競合・信号の戦略入力、を既存機能へ配線する。ローカル検索ランキング要因（GBPシグナル・オンページ/NAP・レビュー・被リンク・行動・引用一貫性・パーソナライズ）は**設計の背景**として扱い、本製品が担うのはこのうちコンテンツ・技術・観測レイヤーである。

- ローカル順位観測（Local Pack／地図／オーガニック分離）: 地域指定（`REQ-KGA-03`）ごとに、対象キーワードのローカルパック順位・地図順位・オーガニック順位を**分離取得**する（DataForSEOの location/device パラメータ、`REQ-SRC-01`の範囲で新規外部依存なし）。ローカルパック該当は proximity・primary category 依存で**本質的に非決定的**である旨をUI・データに明示し、順位保証をしない（`REQ-PACK-10`）。ウォッチリスト（`REQ-KGA-20`）と検索流入分析（`REQ-NAV-04`）に**地域軸**を追加する。
- ローカルインテント検出（決定論）: 「近くの」「near me」「〇〇市/区/駅」等の地域修飾を属性判定（`REQ-KGA-13`の補助属性「地域性」）で分類し、地域ページ／サービスエリアページのコンテンツ候補（`REQ-KGA-18`のkeyword起点）として提示する。地名辞書・修飾語辞書は設定レジストリ（`REQ-ADM-09`）。

- ローカル向けコンテンツ型（地域ページ／サービスエリアページ）: 記事タイプに「地域ページ」を持つ（構成カタログ `REQ-PACK-11`）。地域名×サービスの機械量産は**薄いページ・ドアウェイページを回避**するため、地域固有の一次情報・差別化要素（対応エリア・実績・料金・アクセス等）の入力を必須とし、根拠なき地域主張・実在しない所在の記載はゲート（deceptive_claim／thin、`REQ-PACK-09`）で止める。NAP・営業時間・対応エリアは**ユーザー入力の実在情報**を前提とし、捏造しない。
- 技術シグナル（決定論チェック、`REQ-KGA-21`/`REQ-KGA-09`へ接続）: LocalBusiness／Service 等の構造化データの付与・妥当性、**NAP（名称・住所・電話）のサイト内一貫性**、営業時間・地図情報の整合を技術チェックに加え、不整合は問題一覧として提示し、修正候補をリライト／WP対応の導線へ接続する。判定にLLMを使わない（`REQ-KGA-08`）。
- ローカル競合・信号の戦略入力: ローカルパック上位（地図の掲載事業者）を**ローカル競合集合**として取り込み（`REQ-KGA-18`のSERP面適応・DataForSEO競合バッチ）、上位のカテゴリ・見出し傾向を戦略入力にする。レビュー信号（件数・鮮度・多様性・感情の傾向）は**観測・戦略入力**として扱う（記事の主張・CTA・FAQの手がかり）。レビュー返信・収集・GBP投稿の代行は範囲外と明示する。
- 設定・権限・コスト: 取得の地域/デバイススコープは設定「キーワード取得設定」（`REQ-NAV-04`）で対象サイト単位に指定。ローカル運用の有効化・地域ページ量産の承認はOwner/Admin/Editorの実行権限（`REQ-PRODUCT-08`）と公開前承認（`REQ-WPA-04`）に従う。ローカル順位・構造化チェックは決定論（`REQ-KGA-08`）でクレジット消費なし、外部取得のみ既存の予算・レーン（`REQ-SRC-06`）に従う。

## 23. 動的キーワード戦略レコメンド  ［REQ-KGA-23］

キーワードの優先順位は固定値にしない。市場圧力、サイトの現在地、事業目標、既存コンテンツ、GSC/CV実績の変化に応じて再計算し、`REQ-PRODUCT-24` の記事制作・リライトrecommendationへ供給する。

既存SiteもGSC獲得語だけを診断母集団にせず、公共キーワード資産、業界・商品・顧客候補、ユーザー登録語、GSC Query、適格な検索競合の獲得語を統合したキーワード市場を先に構築する。詳細な市場状態、SERP実績型cluster、代表語、自Site固有難易度、traffic potential range、動的検索競合、Content Gapから施策種別への判定は `logic/keyword-dynamic-recommendation-logic-requirements_v1.md`（`REQ-KRL-02〜08`）を正本とする。

戦略目的は重ね合わせ可能な3軸で保持する。

- `site_necessity`: サイトとして説明責任を果たすために必要な基礎・定義・サービス・信頼形成キーワード。短期流入やCVが小さくても、情報構造、トピック被覆、ドメイン信用性の土台として必要になりうる。
- `traffic_opportunity`: 実現可能な自然検索流入を獲得するキーワード。需要だけでなくAIO・広告占有・順位可能性を反映する。
- `conversion_opportunity`: 商品・サービスとの適合、CV近接、既存CV相関、商用意図を持つキーワード。流入量が小さくても優先されうる。

動的優先度:

- 戦略プロファイルは `foundation`（サイト基盤）/ `growth`（流入拡大）/ `conversion`（CV強化）/ `authority`（信用形成）/ `balanced` を持ち、サイト単位・期間単位で3目的の配分を設定できる。
- 月次目標、コンテンツ不足、サイト公開期間、既存記事数、GSC/CV実績、トピック信用ギャップに応じて推奨プロファイルを提示するが、切替はユーザー承認または許可されたAutopilotに限定する。
- 優先度は `strategic_need × attainable_value × urgency × confidence ÷ cost_and_risk` の成分として保持し、単一スコアだけでなく内訳を表示する。具体式と重みはConfig Registryでversion管理する。
- 同じキーワードでも、サイト基盤が不足する時期は`site_necessity`、流入拡大期は`traffic_opportunity`、収益強化期は`conversion_opportunity`が優先される。過去の優先度を現在の事実として固定しない。
- recommendationは新規作成だけでなく、既存記事への追補、リライト、統合、内部リンク、保護、監視、見送りを選択する。ArticleSummaryで既に満たされている場合は新規記事を抑制する。
- 再計算トリガは、GSC/CV日次更新、SERP面変化、AIO/広告占有変化、ArticleSummary更新、サイト目標変更、施策効果確定、ルールversion変更とする。画面要求時に重い再計算をせず、増分バッチでrecommendation read modelを更新する。
- 根拠が不足する軸はunknownとしてconfidenceを下げる。未知値を0点と同一扱いせず、「低価値」と誤判定しない。
