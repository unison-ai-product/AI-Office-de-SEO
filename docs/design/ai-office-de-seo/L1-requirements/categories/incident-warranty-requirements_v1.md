# AI Office de SEO 障害対応・保証要求

## 1. 責務  ［REQ-IRG-01］

障害の検知、分類、封じ込め、連絡、復旧、補償、再発防止と、サービスが保証する範囲・保証しない範囲を定義する。

本要求の「保証」はサービス提供責任の境界であり、検索順位、流入、CV、売上などのSEO成果保証ではない。契約・法務文言は法務確認済みの利用規約・SLAを最終正本とする。

## 2. 障害分類  ［REQ-IRG-02］

| Severity | 例 | 初動 |
|---|---|---|
| SEV-1 | 全体停止、越境・漏洩疑い、誤公開、課金の広範囲誤り | 即時Kill Switch、責任者招集、外部連絡判断 |
| SEV-2 | 主要機能停止、複数テナント影響、ジョブ大量失敗 | 対象経路停止、代替・縮退、影響顧客通知 |
| SEV-3 | 一部機能劣化、単一テナント障害、性能目標の継続超過 | 回避策提示、優先修正 |
| SEV-4 | 軽微な表示・文言・非主要機能不具合 | 通常バックログ |

Severityは影響範囲、データ機密性、不可逆性、継続時間、顧客業務停止、金銭影響から決定する。報告者や顧客プランだけで低く分類しない。

## 3. 検知と起票  ［REQ-IRG-03］

- SLO、エラー率、遅延、キュー滞留、課金差異、越境試行、公開失敗、Provider異常を監視する。
- 自動検知と顧客申告を同じincident recordへ統合する。
- incidentは `incident_id / severity / status / detected_at / affected_scope / symptoms / owner / timeline / customer_impact / data_impact / financial_impact` を持つ。
- 同一原因のalert stormを集約し、通知大量発生を防ぐ。

## 4. 封じ込め  ［REQ-IRG-04］

- tenant/site、workflow、Provider、外部連携、全体の各粒度でKill Switchを使える。
- 誤公開・誤課金・越境疑いはfail-closeし、影響経路を停止してから調査する。
- 停止時は進行中ジョブをcheckpoint保留し、予約公開を止め、未確定クレジットを解放可能にする。
- 証跡保全と顧客データ最小化を両立し、本文・秘密情報をincident記録へコピーしない。

## 5. 連絡  ［REQ-IRG-05］

- 内部通知、対象顧客通知、公開ステータスの3層を持つ。
- 顧客通知には、確認済み事実、影響、開始時刻、現在の対応、回避策、次回更新予定を含める。
- 原因未確定時に推測を断定しない。更新がなくても約束した時刻に状況を更新する。
- セキュリティ、個人情報、法令報告が関係する場合は、承認済みの連絡・報告手順へエスカレーションする。

## 6. 復旧  ［REQ-IRG-06］

- 復旧順序は、データ整合、安全な読取、手動実行、自動実行、公開・課金の順を既定とする。
- checkpoint再開、冪等再実行、直前版rollback、DB/PITR、テナント別復元を使い分ける。
- 復旧判定はヘルスチェックだけでなく、代表業務のE2E、台帳整合、越境負テストで確認する。
- 復旧後は段階的にtraffic/tenantを戻し、再発時は自動停止する。

## 7. 補償・保証  ［REQ-IRG-07］

- システム障害で失敗したAI実行は原則として使用クレジットを返還する。
- 二重課金、誤ったクレジット確定、未提供サービスは台帳調整と監査証跡を伴って是正する。
- SLA違反時のservice credit、返金、対象プラン、除外条件、申請期限はPricing/SLA Configurationで版管理する。
- 補償は自動判定候補を生成できるが、金銭返金・高額調整は承認権限者の確認を必要とする。
- SEO順位、流入、CV、売上、工数削減値は保証しない。対外表示は成果保証とサービス可用性保証を混同しない。
- 外部Provider、Google、WordPress、顧客環境起因でも、本サービス側の回避・再試行・説明責任は免除されない。契約上の補償対象外と、運用上の対応不要を同一視しない。

## 8. 事後対応  ［REQ-IRG-08］

- SEV-1/2はtimeline、root cause、contributing factors、検知漏れ、再発防止、owner、期限を記録する。
- 個人を原因にせず、設計、テスト、監視、権限、手順の不足へ戻す。
- 恒久対策は要求・設計・テストへback-propagationし、応急処置だけでcloseしない。
- 顧客向け事後報告と内部postmortemを分離し、秘密情報を外部報告へ含めない。

## 9. 演習  ［REQ-IRG-09］

- Kill Switch、Provider停止、DB復元、誤公開停止、課金調整、テナント復元を定期演習する。
- 演習は成功可否、所要時間、手作業、証跡、改善事項を残す。
- 未演習期間、失敗した復旧手順、期限超過した再発防止を管理画面で警告する。

## 10. 受入条件

- [ ] AC-IRG-01: 障害をSEV-1〜4へ一貫した基準で分類できる。
- [ ] AC-IRG-02: tenant/site/workflow/provider/全体の各粒度で封じ込めできる。
- [ ] AC-IRG-03: 顧客通知とステータス更新に確認済み事実・影響・次回更新予定が含まれる。
- [ ] AC-IRG-04: checkpoint、rollback、PITR、テナント復元の選択基準がある。
- [ ] AC-IRG-05: 復旧がE2E・台帳整合・越境負テストで確認される。
- [ ] AC-IRG-06: システム障害のクレジット返還と金銭調整が監査可能である。
- [ ] AC-IRG-07: SLA補償とSEO成果非保証が対外表示で区別される。
- [ ] AC-IRG-08: SEV-1/2の恒久対策が要求・設計・テストへ戻される。
- [ ] AC-IRG-09: 復旧・停止・調整演習が記録される。
- [ ] AC-IRG-10: 外部サービス起因でも回避策・再試行・説明が提供される。
