# AI Office de SEO プロダクト要求 v3.7

## 1. 基本要求  ［REQ-PRODUCT-01］

AI Office de SEOは、マルチテナント、マルチユーザー、マルチアカウント、マルチサイトに対応する。

単位:

- Tenant: 契約・請求・利用上限の単位
- Membership: User × Tenant × Role の所属関係
- User: ログインユーザー
- Connected Account: ユーザーが接続する外部アカウント（Google/GSC、WordPress）
- Site: WordPressサイト、GSCプロパティ、キーワード、記事、CV、ナレッジ、生成ジョブの単位
- Role: Owner / Admin / Editor / Viewer

テナント階層:

```txt
Tenant
  ├── Memberships (User × Role)
  ├── Connected Accounts (Google / WordPress)
  └── Sites
        ├── gsc_property
        ├── wordpress_connection
        ├── keywords / articles / gsc_data_mart / cv_daily / knowledge
        └── jobs
```

マルチテナント・マルチアカウントの前提:

- 1テナントに複数ユーザーが所属できる（Membership）。
- 1ユーザーが複数テナントに所属でき、テナントごとにRoleが異なってよい。
- 1ユーザーが複数のGoogle/GSCアカウント、複数のWordPress接続を持てる。
- 外部アカウント接続とSiteは、常に単一のTenantに属する。テナントをまたいで共有・流用されない。
- ユーザーの操作は常に単一の「アクティブなTenant」コンテキスト内で行われ、テナント間のデータは混在しない。

主要テーブル・主要イベント・主要ジョブ・キャッシュキー・キュー・オブジェクトストレージ・ログは、`tenant_id` と、サイトに閉じるものは `site_id` のスコープを持つ。

## 2. サイト単位サンドボックス  ［REQ-PRODUCT-02］

全AIジョブは、作成時に単一の `tenant_id`、`site_id`、`job_id` に固定される。

AIやクライアントに任意の `tenant_id` / `site_id` を指定させない。DBアクセス、GSC参照、WP送信、Source Pack解決、Ticket実行、Prompt構築は、すべてサーバー側で固定された `SiteSandboxContext` に閉じる。

## 3. URLマスターキー  ［REQ-PRODUCT-03］

記事識別はURLをマスターキーにする。

一意キー:

```txt
tenant_id + site_id + canonical_url_hash
```

WP投稿IDは補助参照とし、主識別子にはしない。URL変更、canonical変更、リダイレクト、GSC旧URL残存に対応するため、URL alias履歴を保持する。

照会（外部向けの参照・突合）はURL（`canonical_url_hash`）で行い、内部の管理・レコード同定は安定な内部IDで行う。URLは変化しうるためエイリアス履歴経由で内部IDへ解決する。同一対象（同一内部ID／同一canonical_url_hash）への重複ジョブ・重複レコードを検出した場合は、ハードロックではなくアラートを出す。

## 4. 記事本文非保持  ［REQ-PRODUCT-04］

新規記事生成・リライト・QA・投稿変換の過程では一時的に本文を扱える。ただし、一時本文はTTL付き領域に置き、完了後に削除する。

例外は1つのみ: **成果物の一時保持（Output Vault。`REQ-WPA-14`）**。喪失防止（WP送信フェイルセーフ）とユーザー可搬性（本文のコピー・ダウンロード）に目的を限定し、暗号化・テナント境界内・監査対象の条件下で、既定14日（Config Registry）まで封入ペイロードを保持し、期限到達で完全削除する。学習・分析等の他用途には使用しない。

恒久保存するのは、本文ではなく、以下である。

- article digest
- section hash
- outline snapshot
- ticket snapshot metadata
- QA result
- WP draft URL
- job usage
- token / credit usage

## 5. GoogleログインとGSC接続  ［REQ-PRODUCT-05］

ユーザーはGoogleログインで開始できる。GSC接続時はSearch Console用のOAuth同意を行い、バックグラウンド同期のために安全にトークンを保持する。

ログイン用のGoogleアカウントと、GSCデータ取得用に接続するGoogleアカウントは別でよい。1ユーザーが複数のGoogle/GSCアカウントを接続でき、各接続は複数のGSCプロパティを持ちうる。

- 各Connected Accountとそのトークンは、接続したTenantに属し、テナントをまたいで参照・利用されない。別テナントで同じGoogleアカウントを使うには、そのテナントで改めて接続する。
- GSCプロパティはSiteに紐づけ、`tenant_id` / `site_id` の境界内でのみ参照する。
- 各接続は個別に失効・再認可・切断でき、切断時は当該トークンを破棄する。

GSCデータは都度API参照ではなく、AI Office de SEO側に日次Data Martとして蓄積する。

## 6. WordPress連携  ［REQ-PRODUCT-06］

WordPressはコンテンツの正本である。SaaS側は、記事生成、改善案作成、下書き反映、予約投稿、成果分析を担当する。

WP連携はオートメーション配下に置き、以下を扱う。

- 接続確認
- サイト情報取得
- 文体指定（です・ます調／だ・である調と、文語体／口語体の組合せ）
- 個別Siteの言い回し学習のON/OFF。ON時はサンプル記事10本を学習入力にする
- 記事サマリー同期
- Dynamic Post Schema導出
- 下書き作成
- 予約投稿
- 公開イベント
- CVイベント

## 7. ユーザー要望とレギュレーション  ［REQ-PRODUCT-07］

ユーザーには「要望」として入力してもらう。これは `User Order Pack` として扱い、強く効きすぎないように影響度を制御する。

レギュレーションは、文末を「です・ます調／だ・である調」から選択し、文章表現を文語体／口語体の組合せで指定できるようにする。専門度、CTA強度、NG表現、根拠厳格度、表現の硬さもフロントから調整可能にする。個別Siteの記事から固有の言い回しを学習する機能は任意でON/OFFでき、OFF時は指定された文体だけを使用する。

User Orderは、SEO証跡、法務・レギュレーション、投稿形式、サンドボックス境界を上書きできない。

要望の一時無効化（soft-disable）: 要望は追加・削除に加えて**一時無効化**でき、削除せずに適用のみを止められる（次の生成から不適用）。**いつでも再有効化**でき、無効中も要望自体と影響帰属の履歴（`REQ-PRODUCT-19`施策台帳・影響履歴）は保持する＝適用対象から外すだけとする。無効状態は `User Order Pack` のコンパイル対象から除外して供給し、有効化で再度含める（`REQ-PACK-02`）。無効化/再有効化はレギュレーション・サイト方針の編集と同じ権限（Owner/Admin/Editor、`REQ-PRODUCT-08`）で行う。

## 9. 提供方針（オンボーディング・ヘルプ）  ［REQ-PRODUCT-09］

初期導入とヘルプの提供形態を、製品ビルドのスコープと分けて定義する。

- オンボーディングはコンサルティングとして提供し、そこで価格を取る。製品側は、自己完結型のオンボーディングUXを作り込むのではなく、WP接続、GSC接続、サンプル記事の指定・取り込み、レギュレーション設定などの各機能を提供し、コンサルがそれを用いて初期設定を行う。
- 個別Siteの言い回し学習をONにする場合は、公開記事からサンプル記事10本を選定する。10本未満の場合も導入を停止せず、利用可能な記事だけによる暫定プロファイルで開始し、信頼度を明示する。学習OFF時はサンプル記事を要求しない。学習ONのSiteには3か月ごとにサンプル見直しを通知し、再学習の実施はユーザーが判断する。製品はこれらの機能を提供し、導入手順の伴走はコンサルが担う。
- アプリ内ヘルプ・FAQは製品スコープに含めない。専用サイト構築で対応する。
- 記事内のFAQ生成機能（faq_answer意味ユニット、FAQブロック、FAQハブ記事タイプ）は本製品の生成機能であり、ヘルプFAQ用の専用サイトとは別物として維持する。
- 登録時に同意書を提示し、公開コンテンツの最終責任はユーザー（サイト運営者）に帰属し、サービスは生成物の最終的な正確性・適法性の責任を負わない旨に同意を得る。あわせて、匿名集計（k匿名・識別子除去）によるサービス品質向上へのデータ利用と、テナント単位のオプトアウト（`REQ-PRODUCT-13`）を同意項目に含める。匿名統計の**公表**（ベンチマーク等）を利用目的に含める場合はその旨を同意文言に明記する（法務レビュー）。個別事例の掲載は本同意に含めず、別途の明示許諾（`REQ-PRODUCT-23`）による。YMYL・規制領域を含め、公開可否の最終判断はユーザー側が行う前提とする（同意文言の確定は法務レビューを要する）。

- 同意の版管理と再同意: 同意書・規約は版管理し、同意記録に**同意した版**を紐付ける。重要変更（利用目的・データ扱い・料金条件の変更等、区分は法務判断=D-16）の版UP時は、次回利用時に差分提示つきで**再同意を要求**し、再同意までは影響範囲の機能を制限できる。軽微変更は通知（`REQ-PRODUCT-16`）のみでよい。文言の自由差し替え（`REQ-NAV-09`）の対象外とする。
## 10. テナント分離方式（ID型論理分離）  ［REQ-PRODUCT-10］

テナント分離は、テナント別の物理DB・物理スキーマ分離ではなく、共有DB上の `tenant_id` / `site_id` による行レベルのID型論理分離を採用する。

- テナント別DB、テナント別スキーマ、専用インスタンスへの物理分離は初期方針として採用しない。
- 全テナント共有のDB・キャッシュ・キュー・オブジェクトストレージを、識別子スコープで論理分離する。
- 物理分離は将来の特別要件（規制・大口契約等）が出た場合にのみ個別検討し、初期のID型論理分離を前提とした設計・要求を崩さない。

ID型論理分離は、単純な列追加ではなく、越境防止の補償的統制（`REQ-SEC-07`）とセットで成立させる。分離方式の実施・強制・監査はセキュリティ要求側で定義する。

## 11. 通知・アラート  ［REQ-PRODUCT-11］

散在していた通知・アラート（カニバリ検知、重複ジョブ、プラグイン更新、SLOアラート等）を、単一の通知基盤として統合定義する。通知は観測用のドメインイベント（`REQ-SEC-13`のイベント購読と同じエンベロープ）から導出し、通知専用のイベント体系を別に作らない。

通知イベントカタログ（既存要求から導出。列挙は拡張可能・初期集合）:

- ユーザー向け（テナント/サイト内）:
  - 承認依頼・差し戻し結果・予約実行結果（`REQ-WPA-04`）→ 既定受信者: 承認権限者（Owner/Admin、`REQ-PRODUCT-08`）
  - hard gate保留（人手判断待ち）（`REQ-AGENT-08`）
  - ジョブ完了・失敗・停止ガード到達による保留（`REQ-AGENT-01` / `REQ-AGENT-06`）
  - カニバリ検知（`REQ-KGA-07`）、重複ジョブ・重複レコード（`REQ-PRODUCT-03`）
  - クレジット残高低下・予約失敗（`REQ-BILL-02`。しきい値は設定レジストリ、`REQ-ADM-09`）
  - サブスクリプション状態変化による機能制限（past_due / unpaid、`REQ-BILL-08`）
  - 接続トークンの失効・再認可要求（`REQ-SEC-09`「失効・エラー時は再認可を促す」の実現経路）
  - Kill Switch作動と承認済み予約の保留戻し（`REQ-DUR-04`）
  - WPプラグイン更新あり（`REQ-WPA-07`。WP管理画面経路は同要求で既定義、in-app通知はその重複経路）
  - 注目キーワード（ロングテール昇格候補のしきい値超過、`REQ-KGA-16`）
  - ウォッチリスト変化・サイト急変検知・SERP/アルゴ変動・季節リフレッシュ期日（`REQ-KGA-20`）
  - インデックス問題の検出（`REQ-KGA-21`）
  - 月次実績サマリ（目標乖離と要因、`REQ-PRODUCT-17`）
  - 運営お知らせ（アナウンス種別、`REQ-PRODUCT-16`。管理者作成の `platform.announcement_published` イベントとして同一エンベロープで投入し、通知専用の別体系を作らない）
  - 共有クォータ超過による低優先ジョブの次窓繰り延べ（`REQ-SRC-07`。既定は通知センター表示のみ、プッシュしない）
- 開発管理者向け（コンソール側）:
  - SLOアラート・インシデント（`REQ-ADM-07`）、Stripe Webhook失敗・reconciliation不一致（`REQ-ADM-02`）、Provider Health Check失敗・Canary rollback（`REQ-BILL-09`）、Prompt Cacheヒット率の下限割れ・原価乖離（`REQ-BILL-06`）、境界違反試行（`REQ-SEC-07`）、接続サイト別プラグインversion集約（`REQ-WPA-07`）、Pack/Catalog版活性化後の品質リグレッション検知（`REQ-ADM-10`）

チャネルと正本:

- in-app通知センターを正本とする。メールは重要イベント（承認依頼、hard gate保留、支払い失敗、再認可要求、Kill Switch作動）の補助チャネルとし、種別ごとにユーザーがON/OFFできる。
- 外部チャネル（メール等）の配信失敗があっても、通知センターの記録は失われない（配信は補助、記録が正本）。
- その他チャネル（チャット連携等）は初期スコープに含めず、追加はconfig駆動の将来拡張とする。

不変条件:

- 通知は `tenant_id`（サイトに閉じるものは `site_id`）境界内で配信し、受信者はRole・Membershipに基づきサーバー側で解決する（`REQ-SEC-08`）。クライアント申告の宛先を信頼しない。
- 通知本文に記事本文全文・プロンプト全文・シークレット・APIキーを含めない（`REQ-SEC-11`）。対象の特定はURL・ジョブID・hash・要約メタで行う。
- 監査対象イベント（Kill Switch・課金操作等）の正本は監査ログ（`REQ-SEC-10`）であり、通知はその写像にすぎない。通知の失敗・未読は監査の成立に影響しない。

頻度制御と設定:

- 同種イベントの連続発生（夜間バッチのカニバリ大量検知等）はダイジェスト化・スロットリングする（初期値・要調整、設定レジストリ管理 `REQ-ADM-09`）。
- 通知設定（種別別ON/OFF・ダイジェスト頻度）はユーザー単位を基本とし、テナント既定で上書き順を持つ。設定画面は第一階層「設定」配下（`REQ-NAV-04`の「通知」の中身をこの要求が定義する）。
- 既読管理・保持期間を持つ（保持期間は初期値・要調整）。

## 12. ユーザーカスタマイズ階梯（意図はユーザー・技巧は製品）  ［REQ-PRODUCT-12］

生成品質は標準装備であり、利用者の熟練に依存させない（Quality Gate＝`REQ-PACK-09`、few-shot単一ソース＝`REQ-PACK-12`）。カスタマイズは「意図（誰向けか・何を主張するか）はユーザーが与え、技巧（構造・文体・プロンプト）は製品が担う」の分担で提供する。プロンプト技巧をユーザー自己サーブに開放しない。

階梯（自己サーブ）:

- Tier 1 レギュレーション調整（既存 `REQ-PRODUCT-07`）: 文体・専門度・CTA強度・NG表現・根拠厳格度・表現の硬さ。
- Tier 2 要望（User Order、既存 `REQ-PACK-02`）: 自由文の要望を soft / normal / strong の影響度で注入。
- Tier 3 戦略入力（ターゲット軸・主張軸）:
  - ターゲット軸: 誰向けか（セグメント・リテラシー・状況）を構造化フィールドで指定する。Domain Positioning の audience / target_axes へ写像し、キーワード管理のターゲット・リテラシーフィルター（`REQ-NAV-04`）と Needs Met 判定（`REQ-PACK-09`）の入力にする。
  - 主張軸: 押したい主張・避けたい主張・差別化の立ち位置を構造化フィールドで指定する。Domain Positioning の `allowed_claims[]` / `avoided_claims[]` へ写像し、Research/Outline と執筆の制約にする。

文体・構造のカスタム経路（自己サーブにしない）:

- 文体・書き方: ユーザー自作のfew-shot登録は提供しない。文末は「です・ます調／だ・である調」、文章表現は文語体／口語体の組合せから指定する。個別Siteの言い回し学習をONにした場合だけ、選定したサンプル記事10本からPack Compiler（`REQ-PACK-16`）がContent Regulation Packを作成する。10本未満は暫定プロファイルとする。OFF時はSite記事由来の言い回しを適用しない。
- 記事構造・レシピ: `custom_recipe`（`REQ-AGENT-09`のモード）は、ユーザー自己サーブの定義機能ではなく、コンサルティング（`REQ-PRODUCT-09`の提供方針）でヒアリングした個別要件を開発管理者がPack・プロンプト・ゲート管理画面（`REQ-ADM-10`）から登録する運用経路とする。登録後はそのテナント/サイトのスコープでCatalogとして版固定される。

提供しないもの（境界）:

- 生system promptの編集・閲覧、Pack本文・few-shotの直接編集（`REQ-ADM-10`の領分）、Quality Gate判定の無効化・合格値への改変（hard gate例外公開は判定を残したまま二段階確認＋版付き同意＋監査で扱う）、サンドボックス・規制・投稿形式・SEO証跡の上書き（`REQ-PRODUCT-07`を全Tierに適用）。

品質保護（主張軸にも適用）:

1. 保存時Validate: ターゲット軸・主張軸の登録時に静的検査（NG表現・スキーマ・明白な断定表現の検出。機械判定＝`REQ-KGA-08`）を行い、不合格は理由つきで差し戻す。
2. ゲート・バックストップ: 主張は実行時に claim_evidence / eeat_trust / deceptive_claim / ymyl_bar（`REQ-PACK-09`）で検証され、根拠を伴えない主張・YMYL重大不合格はhardで保留になる。ユーザー指定の主張であってもhardは緩まない。
3. 影響帰属: 注入されたUser Order・主張軸・ターゲット軸のキーを観測ログ（`REQ-SEC-02`）とQA結果に紐づけ、ゲート不合格時に「どの指定が影響したか」を生成プレビュー/QA画面で提示し、見直し導線を出す。品質低下の原因帰属を明確にし、製品品質への誤帰属を防ぐ。
4. 事前提示: strong指定・主張軸の適用は品質影響の注意とPreflight見積（`REQ-SEC-12`）へ反映する。

構造的保証: いずれのTierも Packキーインジェクターの取得→注入経路（`REQ-AGENT-07`、Layer B/D）に乗り、固定制約を上書きできない。最終責任のユーザー帰属（`REQ-PRODUCT-09`）と整合する。Tier 3のプラン許可・既定は設定レジストリで管理する（初期値: 要調整）。

## 13. ネットワーク学習（ソース精度の集合知還流）  ［REQ-PRODUCT-13］

利用テナント・利用量の増加に比例して、**ソース（データ・辞書・統計prior・しきい値較正）の精度が向上する**還流ループを持つ。エージェントの挙動側（プロンプト・few-shot・生成方針）へのテナント横断学習は行わない——バイアス混入と挙動の不透明化を避け、改善対象を決定論的なソース側に限定する。

還流ループ（すべて機械判定・`REQ-KGA-08`）:

1. 公共キーワード資産プール: 公開市場または利用条件上再利用可能な外部データ源から取得したキーワードを、キーワード×言語×地域×デバイスを基本キーとする共有資産として大量・長期保持する。正規化形、表記揺れ、関連語・質問・類語、entity、カテゴリ、検索意図、検索量履歴、季節性、競争性、CPC、SERP機能、AIO・広告面、取得元、取得日時、freshness、利用条件、解析versionを蓄積し、Siteごとの初回探索、分類、クラスタリング、価値評価で再利用する。公共観測の更新結果は履歴または時系列集約として保持し、単なるTTLキャッシュ消去で資産を失わない。SERP本文・第三者記事本文は保持対象に含めない。
2. 共有観測キャッシュ: SERP・AIO観測・PAA・News等の更新取得物は、公共キーワード資産プールに接続する共有キャッシュとして全テナントで再利用する（キャッシュ2層区分は`REQ-SEC-07`）。カバレッジ・鮮度が利用量に比例して向上し、同一条件の外部API再取得を抑える。
3. 辞書の集合知: co-landing由来のエイリアス候補（`REQ-KGA-15`）、modifier/entity/業界辞書の候補（`REQ-KGA-13`）は、**k匿名しきい値（N以上の独立したテナント/サイトで観測、Nは設定値）**を満たしたもののみ、グローバル辞書候補へ昇格提案する。候補は言語的対のみで、URL・サイト・テナント識別子・流入量の内訳を含めない。
4. 統計prior: 期待CTR基線（`REQ-KGA-17`）・Quality Gate計測分布（`REQ-PACK-10`）・カニバリ/リライトしきい値（`REQ-KGA-07`/`REQ-KGA-08`）のテナント横断集計を、セグメント（intent・デバイス・業界／業種・AIO観測有無）別priorとして提供する。Siteの分類は「業界／業種」の2階層を複数持てる構造とし、標準Catalogからの選択とユーザー追加を許可する。複数分類は優先順で指定し、配分比率は記事数・キーワード・実績・横断軸から算出する。横断軸は対象顧客、共通課題、商品・サービス、地域、ファネルと補足記述を持つ。

   業界／業種が未設定の場合はキーワード、Article Summary、商品・サービス、対象顧客、サイト構造から推定し、confidence、根拠、精度非保証を表示する。新規サイトは該当する複数の業界／業種priorを横断軸で調整した値から開始し、自サイトデータの蓄積に応じて自サイト実測へ縮小推定で移行する（コールドスタート解消）。同意・匿名化・k匿名条件を満たす登録Siteが増えるほど、業界／業種別priorと推定較正の標本を増やせる構造とする。集計はメトリクスのみで本文・URL・クエリ文字列を含めない。

   ユーザーが推定分類を修正・確定した場合は確定値を正本とし、自動推定で上書きしない。修正前後をキーワード分配、記事分類、Site分析、業界推定の教師データとしてSite内較正へ使用し、同意・匿名化・k匿名条件を満たす場合だけ全体較正へ集約する。複数業界の優先方式はユーザー指定または自動を選択できる。分類変更時はユーザー指定予定を維持し、システム自動予約の未実行項目だけを再検証する。
5. 成果較正: リライト種別×改善率等の匿名集計で、しきい値初期値の較正提案を生成する。

適用の統制（自動反映しない）:

- 集約が生むのは常に**提案**であり、適用は既存の統制経路のみ: 辞書・タクソノミ→Catalog改版（`REQ-ADM-10`のdraft→Preview→Validate→Approve→Publish）、prior・しきい値→設定レジストリ改版（`REQ-ADM-09`の影響プレビュー・版管理）。版固定によりジョブ再現性を壊さない（`REQ-PACK-04`）。
- 集約はテナント→グローバルの一方向で、生データはテナント境界内に留まる。集約結果からテナント・サイト・個別URLを特定できないこと（k匿名・識別子除去）を集約パイプラインの契約検証（`REQ-SEC-13`）に含める。
- 公共キーワード資産プールへ格納できるキーワード文字列は、公共外部データとして独立取得でき、取得元の保存・再利用条件を満たすものに限定する。GSCだけで観測したクエリ、ユーザーだけが登録した語、Site・商品・顧客・CVとの対応、URL、順位、クリック、表示、CV等の顧客固有情報はプールへ直接格納しない。同一語を公共外部データから独立取得できた場合も、顧客との対応を除去して公共データとして登録する。
- 対象外（横断学習しない）: 記事内容・見出し・digest、Domain Positioning・User Order・ターゲット軸・主張軸などのサイト戦略、few-shot・Prompt Pack内容、エージェントのプロンプト構成。
- 同意とオプトアウト: 登録時同意に「匿名集計によるサービス品質向上へのデータ利用」を含め（`REQ-PRODUCT-09`。文言は法務レビュー）、テナント単位のオプトアウトを提供する。オプトアウトテナントのデータは集約から除外され、共有観測キャッシュ（公共データの再利用）と辞書・priorの**受益**は継続する。オプトアウト操作は設定画面（`REQ-NAV-04`の設定）に置き、Owner/Adminに限定する（`REQ-PRODUCT-08`）。
- 偏りへの注意: 初期テナント構成の業界偏りがpriorへ乗るため、セグメント別prior＋グローバルfallbackの階層とし、セグメント標本数がしきい値未満の場合はグローバルpriorのみを用いる（初期値・要調整）。

サンドボックスとの整合:

- ジョブ（`SiteSandboxContext`内）は共有物（グローバルCatalog・共有観測キャッシュ・prior）の**読み取り専用の消費者**であり、ジョブ開始時のversion freezeで参照が固定される。ジョブ・Executorから共有物への書き込み・集約の起動はできない（`REQ-PACK-06`のホワイトリストと境界検証）。
- 集約はジョブ経路の外の専用バッチであり、テナント横断集計のdefault-deny（`REQ-SEC-07`）に対する**唯一の明示認可例外**として、専用システムロール・到達不能性・k匿名出力限定・監査を条件に実行する。
- コスト計上: 共有観測キャッシュを温める初回fetchの費用は`REQ-SRC-07`のグローバル/フェアシェア予算へ計上し、**共有キャッシュの読み取りは読む側テナントの外部API予算を消費しない**（共有の経済メリットを帳簿上も成立させる）。集約バッチ自体の費用はテナント課金外の運用費とする。

## 14. 分析データエクスポート  ［REQ-PRODUCT-14］

キーワード管理・検索流入分析・ジョブ履歴の表示データをCSV等でエクスポートできる。対象はテナント境界内・実行Roleの閲覧権限内に限る（`REQ-SEC-08`）。記事本文・プロンプト・シークレットは対象外（本文非保持原則 `REQ-SEC-11`）。行数上限・レート・形式は設定レジストリ管理（`REQ-ADM-09`）。実行は監査対象ではなく通常操作ログ（`REQ-SEC-02`）に記録する。

## 15. グローバル検索  ［REQ-PRODUCT-15］

ヘッダー常設のグローバル検索（`REQ-NAV-02`のグローバル要素）で、テナント内のキーワード・記事（タイトル/URL/メタ）・ジョブ・通知・設定項目を横断検索し、対象画面へ遷移できる。検索対象は列挙制（本文全文は対象外＝非保持）で、結果はRole可視性に従う。

## 16. 運営お知らせ・ステータス  ［REQ-PRODUCT-16］

- 運営お知らせ: 開発管理者が作成・配信するアナウンス種別を通知基盤（`REQ-PRODUCT-11`）に追加する。対象（全体/プラン/テナント）を選択して配信し、通知センターに表示（メールは重要時のみ任意）。配信は `platform.announcement_published` イベント（Gate A-1・共通エンベロープ）として投入し、通知はイベント由来とする原則（`REQ-PRODUCT-11`）を維持する。配信はスロットリングし、作成・配信は監査ログに残る（`REQ-ADM-06`）。
- 公開ステータスページ: サービス稼働状況の公開ページを持ち（運用は`REQ-ADM-07`のSLO/インシデント管理と接続）、ユーザーUIのヘルプ近傍に参照導線を常設する。

## 17. 月次プランニング（目標・配分・予測・実績）  ［REQ-PRODUCT-17］

- 目標: 月次のトラフィック/CV目標をサイト単位で設定できる。
- 配分計画: 目標に対する新規作成・リライトの本数配分をカテゴリ/トピック別に計画し、トポロジー（`REQ-KGA-19`）と価値スコア（`REQ-KGA-17`）から推奨配分を提示する（採否はユーザー）。
- 予測: SiteのGSCクリックが直近1か月で1,000件へ到達した後、過去実績（GSC日次・CV・季節性 `REQ-KGA-20`）から計測可能な記事だけ、決定論の**参考レンジ**として提示する。予測可能記事とデータ不足記事を分け、予測可能数・ロック数・不足理由を表示する。実績不足時は市場情報、サイトとして必要な情報、商品・顧客・CV定義から方向性だけを推薦する。点予測・順位/流入の保証をしない。
- 追跡: 日次/週次の進捗と、記事・施策単位の1か月・3か月・6か月評価、月末の実績・乖離要因（急変検知 `REQ-KGA-20`と接続）を表示し、翌月計画の入力にする。表示はダッシュボード内のプランニングタブ（第一階層7項目は増やさない、`REQ-NAV-01`）。

## 18. 自動運用の資源・変更ガバナンス  ［REQ-PRODUCT-18］

完全自動運用（full_auto / Autopilot、`REQ-WPA-04`）と常時監視（`REQ-KGA-19`〜`REQ-KGA-21`、`REQ-PRODUCT-17`）を、メモリ・コストを圧迫しない形で成立させる横断原則。

- 増分計算の原則: 監視・再計算（マッチ、属性、トポロジー再調整、ウォッチ、季節、インデックス、予測）は**変化駆動＝O(変化量)**とする。処理対象は新着GSC日次分・変化した記事/キーワード/ノードに限り、全件再計算は較正・辞書改版時等の明示バッチに限定する（`REQ-SRC-05`のcheckpoint/冪等と接続）。
- 監視の階層化: 常時計算はサイト集計値レベル（軽量な決定論、`REQ-KGA-08`）に限り、詳細分解（要因ドリルダウン）は異常検知時・ユーザー要求時のオンデマンド計算とする。全キーワードの常時個別監視はせず、個別監視はウォッチリスト（`REQ-KGA-20`）に限る。
- 常駐状態の禁止: 監視状態は事前計算結果としてDBに置き、プロセス常駐メモリに全テナント状態を持たない。監視ジョブはバッチ/イベント駆動で起動・終了し、Kill Switch（`REQ-DUR-04`）とADM-S4のコスト観測の配下に置く。
- 変更予算（自己増殖の防止）: リライト・リンク再調整には**日次/週次の生成・下書き予算**（本数・クレジット上限）と、**同一記事のクールダウン期間**、**振動検知**（同一対象への相互打ち消し・往復変更の検出→自動停止＋通知）を設ける。リライトと全文再生成はWP下書きまで自動化できるが、公開記事への反映はユーザー承認を必須とする。収束条件・停止ガードは`REQ-AGENT-06`と同型で、上限到達時は候補をキューに保留し人へ提示する。しきい値はすべて設定レジストリ（`REQ-ADM-09`）。
- 記事利用枠: 各プランに月間・週次の生成クレジット枠を設け、選択品質ごとの1記事当たり予測クレジットから作成可能本数を算出する。プラン内利用枠を超える実行は追加クレジットを消費するが、追加クレジットはWordPress・外部API・実行基盤の安全上の同時実行・レート上限を解除しない。
- コスト帰属: 決定論の監視・増分計算はクレジット消費なし（プラン原価に織込む運用費。原価はADM-S4で観測、`REQ-BILL-06`/`REQ-ADM-04`）。外部API・LLMを使う処理のみ既存の予算・クレジット・レーン（`REQ-SRC-06`/`REQ-SEC-12`/`REQ-BILL-11`）に従う。

## 19. 調査知識の小型蓄積（Derived Facts / 施策台帳）  ［REQ-PRODUCT-19］

外部調査・実行結果から得た知識を、**再調査コストを下げる小さな事実**として蓄積する。TTL付き生キャッシュ（`REQ-SRC-06`/`REQ-SRC-08`＝取得物の再利用）とは目的が異なる、恒久・軽量の層。

- 導出事実ストア（Derived Facts）: 調査から得た低変化の事実（例: SERP面構成タイプ・AIO観測・競合の記事タイプ分布・上位見出しトピック集合・季節パターン）を、`{fact_key, value(数値/enum/短配列), observed_at, confidence, source_ref}` のコンパクト形でテナント/サイトスコープに蓄積する。通常の推薦更新は週次を基本とする。AIO・AI回答面観測は初期提供を確約せず、将来提供時の頻度基準案を月次とする。順位急変・SERP変動時は即時の施策推薦やAIO再取得を行わず、要監視キューへ移して継続観測する。
- 施策台帳（Intervention Ledger）: ページの公開・更新イベントと、リライト種別・リンク調整・CTA変更・季節リフレッシュ等の施策を、施策タイプ×文脈（記事タイプ・intent・階層tier）×効果デルタで記録する。公開・更新から1か月後に一次評価、3か月後に二次評価、6か月後に長期評価を行う。評価はKeyword Map／Assignment Ledgerで割り当てたプライマリ＋セカンダリの同一SERP／intentクラスタへの順位付与を起点とし、順位なしはインデックス診断へ送る。診断内容はユーザーへエスカレーションし、サイト構築・サイト全体設定を責務としない本システムから自動修復しない。CVなし単体は失敗とせず、十分なクリック母数がある場合だけCVRを評価する。セカンダリ優位時は主従を単純に入れ替えず、業界別実績からクラスタ・代表語・主従重みを再計算してロジック補正へ戻す。検索ボリューム・表示回数による季節性／需要変化と、AIO・リスティング出現率による市場圧力を分離する。結果はSite内較正と同意・匿名化済みネットワーク学習の成果較正（`REQ-PRODUCT-13`④）の正式な入力とする。
- 小ささの規約: 事実・台帳は正規化キー＋数値/enum＋出典参照のみで構成し、**本文・生HTML・SERPスナップショット全文を持たない**（`REQ-SEC-11`と同型）。サイト当たりのサイズ上限と世代管理を持ち、古い日次事実は月次統計へロールアップして肥大を防ぐ（上限・期間は`REQ-ADM-09`）。
- 書き込みガード（幻覚の永続化防止）: 導出事実の書き込みは、Executorの直接書き込みではなく**Snapshot経由で管理層がスキーマ検証後に反映**する（`REQ-PACK-06`と同型）。`source_ref` は必須とし、**sources_used内の根拠を参照できない事実は永続化を拒否**する（LLMの推測・幻覚を恒久層へ昇格させない）。`confidence`・鮮度期限（`observed_at`＋期限）も必須で、期限なしの恒久事実を作らない。
- 供給経路: 生成・リライトへの供給はSource Pack経由（`source.site.facts.v1`、`REQ-PACK-07`）。テナント横断への昇格は常にk匿名のネットワーク学習経路（`REQ-PRODUCT-13`）のみ。

## 20. 記事能力サマリーと軽量意味索引  ［REQ-PRODUCT-20］

本文非保持（`REQ-PRODUCT-04`）を維持しながらレコメンドの精度を高めるため、ArticleSummaryを単なる要約文ではなく、**その記事が何を持ち、何を満たし、何が不足しているかを表す記事能力インベントリ**として定義する。推薦、候補抽出、一覧表示では本文を取得せず、このインベントリを一次入力にする。

- 基本メタデータ: canonical URL参照、タイトル、meta、H1、見出しツリー、記事タイプ、公開日、更新日、word count、content hash、summary schema version、解析日時。
- 内容インベントリ: 短い要旨、主要トピック、補助トピック、検索意図、対象読者、ファネル段階、対象キーワードグループ、扱う問い、主要な主張、根拠・事例・定義・手順・比較・FAQなどの意味ユニット種別、固有表現・製品・サービス・地域・人物等の重要エンティティ。
- 業務インベントリ: tier、カテゴリ、タグ、CVポイント、CTA種別、内部リンクの送出先・受入可能トピック、保護対象、記事鮮度、更新期限、品質・信頼度・解析完全性。
- 不足インベントリ: 未充足の問い、薄いトピック、古い事実、根拠不足、重複可能性、意図ずれ、CTA不足、内部リンク不足を、本文引用ではなく分類キー・短い理由・根拠参照で保持する。
- 本文非保持: **本文全文、段落テキスト、長い引用、生HTMLは保持しない。** 主張・問い・根拠は短い正規化表現と位置参照（heading key、意味ユニット種別、source hash）だけを持つ。
- 差分更新: WordPress同期、生成、公開、リライト時にcontent hashを比較し、未変更記事は再解析しない。変更記事だけ本文を一時取得して解析し、ArticleSummaryを置換後、本文ワークスペースを破棄する。
- 解析統制: summary schema、抽出器、辞書、モデル、プロンプトはversion固定する。解析失敗や部分取得では旧サマリーを消さず、鮮度と完全性を下げて再試行対象にする。LLM推測だけで事実を補完しない。
- 推薦用途: 新規記事候補、リライト候補、Query Drift修復、カニバリ統合、内部リンク、トピッククラスタ、CTA/CRO、季節更新、好調記事保護をArticleSummary、Keyword Map、GSC実績、施策台帳の組み合わせから生成する。
- 説明可能性: recommendation itemは、対象記事、推薦種別、期待する改善、使用したsummary field、GSCまたはルール根拠、信頼度、鮮度、反証条件を持つ。本文を再取得しなければ説明できない推薦を一覧の既定経路で作らない。
- フィードバック: 採用、却下、編集、保留、実施後効果をrecommendation feedbackへ戻し、推薦種別・記事タイプ・意図・サイト文脈ごとの優先順位較正に使う。ユーザー操作の詳細セッションログは保持しない。
- 軽量意味索引（オプションの補助信号）: **記事能力サマリー由来に限り**埋め込みベクトルを保持できる。用途は、内部リンク・横断タグの候補、重複/カニバリの予備スクリーニング、未マッチクエリの近傍候補、グローバル検索の補助に限定する。**必須経路にはせず**、決定論の一次判定に対する候補絞り込み・並べ替えの補助に留める（`REQ-KGA-08`）。
- 容量統制: 配列項目ごとに件数・文字数上限を持ち、低重要度項目を無制限に追加しない。古い世代は監査に必要なメタデータだけ残し、サマリー本体の全世代を恒久保持しない。
- 観測: 本文取得省略率、サマリー生成時間、1記事当たり保存量、再解析率、推薦候補生成時間、推薦採用率、実施後効果をADM-S4で観測する。

## 21. メール配信基盤（通知メールの送達性）  ［REQ-PRODUCT-21］

通知のメール補助チャネル（`REQ-PRODUCT-11`）の実装面。**in-app通知センターが正本**である原則は不変で、本要求はメールの届く力を担保する。

- 送信抽象化: メール送信プロバイダはアダプタで抽象化し（Provider Registryと同思想、`REQ-BILL-09`）、差し替え可能とする。選定はL3（検証ログ）。
- 送達性: 送信ドメインのSPF・DKIM・DMARCを整備し、通知種別ごとのFrom/テンプレート（テンプレはCatalog管理、`REQ-ADM-10`）を持つ。
- バウンス・苦情処理: ハードバウンス・苦情（spam報告）を受信・記録し、**連続バウンス先はメールチャネルを自動停止**（抑制リスト）して該当ユーザーのin-app通知と設定画面に状態表示・再有効化導線を出す（`REQ-PRODUCT-11`の「配信失敗でも記録は失われない」原則と整合）。
- レート・スロットル: 送信レート制御とダイジェスト（`REQ-PRODUCT-11`）で大量同報を抑制する。送達性指標（バウンス率・苦情率）はADM-S1で監視し、しきい値超過を管理者へ通知する。
- 送信の信頼性: 送信はキュー経由でリトライ（指数バックオフ・上限）を持ち、イベントの`dedupe_key`（Gate A-1）で**同一通知の二重送信を防止**する。認証・回復系メール（`REQ-SEC-16`）は通知より優先の送信レーンとする。
- 運用方針: 通知はno-reply送信とし、返信先としてサポート窓口（ヘルプサイト`REQ-PRODUCT-09`）を明示する。DMARC集約レポートを取り込み送達性の劣化を監視する。**staging等の非本番環境からの実送信を禁止**し、送信キャプチャ（テストモード）で検証する（`REQ-DUR-07`の環境分離）。

## 22. サポート運用（AIファースト・エスカレーション）  ［REQ-PRODUCT-22］

少人数で回すことを設計目標とするサポート窓口。一次応答はAI、人は例外処理に集中する。

- チャネル: in-appサポートパネル（グローバルヘルプから起動、W10）を正とし、メール窓口（`REQ-PRODUCT-21`の返信先）はチケットへ取り込む。
- チャット型QA（一次応答）: ヘルプサイト・FAQ（`REQ-PRODUCT-09`が情報源の正本）を根拠とするAI応答。統制——①回答は**根拠（該当ヘルプ項目）つき**で提示し、根拠のない断定をしない、②テナントデータの参照は**問い合わせユーザー自身のRole・スコープ内の情報**（自分のジョブ状態・エラーコード・通知・請求状態）に限定する（`REQ-SEC-07`/`REQ-SEC-08`。サポートAIに横断権限を与えない）、③**確信が低い・範囲外はエスカレーションを提案**する（捏造しない）、④会話レート・長さ上限（`REQ-SEC-15`）。コストはクレジット外の運用原価（`REQ-PRODUCT-18`帰属、モデルは`REQ-BILL-09`のRouting配下）。
- 自動返信: チケット受付確認（チケットID・SLA目安）・営業時間外案内。**進行中インシデント（`REQ-ADM-07`）がある場合、該当カテゴリの問い合わせへステータスページ（`REQ-PRODUCT-16`）を自動案内**する。
- エスカレーション: AI未解決・ユーザー明示要求・高リスク種別（課金争議・データ・セキュリティ・オーナー回復=`REQ-SEC-16`）は人へ。優先度（severity×プラン）とSLA目安（初期値・要調整、`REQ-ADM-09`）を持ち、エスカレーション時は**AI会話の要約と文脈参照**（tenant/ジョブID・エラーコード。記事本文・プロンプト全文は含めない=`REQ-SEC-11`）をチケットへ添付する。
- チケット管理（管理側 ADM-S12）: キュー・状態・担当・SLA監視・定型返信、期限付き顧客調査（ADM-S9）への権限申請導線。顧客データの操作はPlatform Adminが対象顧客・Site・操作・期限を指定してManagerへ付与し、Operatorは開発・運用ログ確認に限定する。**解決内容のナレッジ還流**（FAQ/ヘルプ更新の起票→`REQ-ADM-10`統制で公開）により一次解決率を継続改善する。
- 計測: 一次解決率（deflection）・エスカレーション率・SLA遵守・チケット量/テナントを観測し（ADM-S12/ADM-S1）、「少人数で回る」をKPIで検証可能にする。
- 保持: サポート会話・チケットはサポート目的で保持（期間は設定）。ユーザー通知はチケット更新イベント（`REQ-PRODUCT-11`）で行う。

## 23. マスターテナント（ドッグフーディング・プレミアム）  ［REQ-PRODUCT-23］

運営自身が本サービスで自社サイト（サービスLP・ブログ）のSEOを運用し、自己サービスを宣伝する記事を作成・公開するための内部テナント。マーケティング施策・恒常的な本番検証・実コストのリファレンスを兼ねる。

- 大原則（特別扱いは課金のみ）: マスターテナントは`tenant.kind=internal`として識別するが、**サンドボックス・品質ゲート・承認フロー・レーン・変更予算・監査は一般テナントと完全に同一経路**を通す。ゲート緩和・境界例外等のバックドアを作らない（本番検証の成立条件かつセキュリティ要件）。
- 課金: Stripe非接続の内部課金モード（内部クレジット付与・消費/原価は通常どおり計測しADM-S4へ計上=**1社分の実コストの生きたリファレンス**。`REQ-BILL-07`台帳・`REQ-ADM-04`）。粗利計算からは内部利用として区分する（`REQ-ADM-02`）。
- 自己宣伝コンテンツの品質: 自社サービスの紹介・比較・事例記事にも deceptive_claim / eeat_trust / ymyl_bar 等のゲートを**同基準で適用**し、根拠なき優位主張・誇大表現を通さない（`REQ-PACK-09`。順位・成果を保証しない誠実表記`REQ-PACK-10`は自社記事でも維持）。主張軸・ターゲット軸（`REQ-PRODUCT-12`）に自社のポジショニングを通常機能として設定する。
- 先行運用（プレミアムの実体）: Feature Flag（`REQ-DUR-04`）のロールアウト順序を **master→canary→一般** とし、新機能・新Pack版・新しきい値をマスターで先行検証する。先行有効化はマスターにのみ許可される設定とする。
- 成果の転用: 自社運用の実績（マッチ率・改善前後・施策台帳）はマーケ素材・ヘルプの実例・デモへ転用できる（自社データのため同意条項の制約外。転用時も第三者情報・個人情報を含めない）。デモ用サイトはマスターテナント配下のサイトとして持てる。
- ネットワーク学習との関係: マスター由来データの集計（`REQ-PRODUCT-13`）への包含は**除外または重み制御**を設定で選べる（自社ドメイン偏りのprior注入を防ぐ。初期値: prior算入は除外・共有観測キャッシュ=公共データは通常どおり）。
- 所有と配下: マスターテナントは**開発者アカウント（運営組織）配下**の資産とし、プロビジョニング・区分変更・廃止はADM-S9からのみ行う（セルフサインアップ経路では作成できない）。
- 統制: 運営メンバーはMembership/Roleで通常ログインし（開発管理者権限とテナントRoleの分離維持、`REQ-ADM-06`）、操作は通常の監査対象。

実績→SEOのループ（SEOビジネス構造の反映）:

- 循環の定義: 顧客実績 → 事例・ベンチマーク記事の素材 → マスターテナントで記事化（通常ゲート適用）→ 検索流入 → リード・販売 → 新たな実績。販売実績がそのままSEO資産になる構造を製品機能として持つ。
- 素材の二層:
  - 層A（k匿名ベンチマーク）: ネットワーク学習の集計（`REQ-PRODUCT-13`）由来の匿名統計（改善率分布・業界別傾向等）。**公表利用は同意の利用目的に明記されている場合に限る**（`REQ-PRODUCT-09`改訂・法務レビュー）。公表時は最小標本数しきい値を課す。
  - 層B（個別事例）: 顧客名・具体数値を含む事例は、**テナント単位の明示オプトイン許諾**（許諾範囲の指定・いつでも撤回可・撤回で以後の利用停止と素材削除）による。許諾はS7で管理し（付与・撤回はOwner/Adminに限定、`REQ-PRODUCT-08`）、許諾台帳はADM-S9。
- 転用経路: 事例転用は横断アクセスdefault-denyの**第二の明示認可例外**（`REQ-SEC-07`改訂）として、許諾範囲フィールドのみを転用時点のスナップショットとしてshowcaseストアへコピーし、マスターテナントのスコープ資産として`source.showcase.cases.v1`（`REQ-PACK-07`）で供給する。全転用・撤回は監査ログに残る。
- 生成の規律: 事例・ベンチマーク記事も通常の品質ゲート（誇大・根拠・誠実表記）を同基準で通す。成果の断定・保証表現は不可（`REQ-PACK-10`）。

## 24. レコメンド主導の記事運用  ［REQ-PRODUCT-24］

記事制作とリライトは、レコメンドから開始する運用を基本とする。ユーザーは「何を作るか・何を直すか」を毎回ゼロから探索するのではなく、システムがArticleSummary、Keyword Map、GSC、競合構造、サイトトポロジー、施策台帳から作った候補を確認し、採用、編集、保留、却下、予約する。

- 主導線: ダッシュボードとコンテンツ作成画面の既定入口は、優先順位付きのrecommendation queueとする。自由なキーワード指定、URL指定、手動起動は補助導線として残す。
- 推薦判定: 各候補はAction Routing Mapの正規typeを持つ。旧判定名`create_new / merge_or_canonicalize / internal_link / cta_update / do_nothing`は、それぞれ`new_article / structure_change_proposal / internal_link_patch / cta_patch / no_action`へ正規化し、`refresh`は`rewrite`のsubtypeとする。記事本数を増やすことだけを正解とせず、統合提案、保護、監視、見送りを正式な結果として扱う。
- 新規記事: 未充足の検索意図・問い・トピック、既存記事との重複、サイト内での役割、期待価値、作成順序を提示する。既存ArticleSummaryで十分に満たされている場合は新規生成を推奨しない。
- リライト: GSC Query Drift、順位・CTR、ArticleSummaryの不足・鮮度・意図ずれ、競合差分、施策履歴から、対象範囲と修正理由を提示する。本文全体を無条件に再生成せず、変更範囲を最小化する。
- 実行契約: recommendation itemを採用すると、対象、目的、根拠、期待改善、変更範囲、品質条件、予算を引き継いだTicketまたはEdit Planを生成する。ユーザーが同じ情報を再入力しない。
- バッチと個別: 複数候補をまとめて採用できるが、予算、変更上限、重複、好調記事保護、公開承認は個別に検証する。レコメンド表示と実行許可を分離する。
- 優先順位: 価値、緊急性、信頼度、実行費用、リスク、記事間依存、直近変更、クールダウンを構成要素として表示する。単一の不透明な総合点だけで順位を決めない。
- キーワード戦略: 新規記事・リライトの優先順位は、市場圧力（AIO・リスティング広告・トピック単位のドメイン信用性）と、戦略目的（サイトとして必要・流入機会・CV機会）の動的配分を使用する（`REQ-KGA-17/23`）。
- 鮮度と再評価: 入力データ、ArticleSummary、ルールversionの更新で候補を再評価する。根拠が古い候補は自動実行せず、stale表示または失効とする。
- フィードバック: 採用、編集、却下、保留理由と実施後効果を、サイト・記事タイプ・推薦種別単位の較正へ利用する。却下を失敗扱いせず、同じ不適切候補の反復抑制に使う。
- UI: 候補には「なぜ今か」「なぜこの対象か」「何を変えるか」「実行しない場合」「費用・リスク」を短く表示し、詳細で根拠を確認できる。本文を読み込まなければ候補一覧が表示できない設計にしない。
