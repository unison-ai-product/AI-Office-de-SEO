通常ビューのマスター・ディテール配線への推奨（2026-07-09相談）:

1. 線引き基準: ドッキングパネル=行を連続切替しながら比較・操作するワークフロー（要約＋アクションまで）／モーダル=単発の長文読解・編集フォーム（全幅が必要）。S2の既存右パネルはopt-in・折りたたみ可・操作補助なので見やすさ原則に適合。
2. パネルの深さ上限=「そのタブの目的完遂に必要な情報まで」。分析・読解・NEXT ACTIONはOfficeの領分。各パネル末尾に「Officeで開く」導線を必置し2モード原則をUIで宣言。
3. S3=ハイブリッド: 行選択→メタ要約パネル（割当KW/ステータス/文字数/QAサマリ/直近履歴/CTA2つ）、本文プレビューはモーダル維持。Office型A記事版とフィールドを揃えない（共通化は正本データであって表示フィールド数ではない。「同じ数値・違う深さ」）。
4. S5: 通常=現状スナップショット＋編集起動、Office=分析・関連・NEXT ACTION。同じ数値の重複はOK（正本同一なら信頼を作る）。編集モーダルは維持しパネル内から起動に統合。
5. データ源泉: 通常ビューにも持ち込む。語彙(MARKET/PERFORMANCE, GSC/DFS)は両モード完全一致、表現は軽量化（8-9px monoソースラベル程度、段分けヘッダー不要）。
6. テンプレ化P0: 選択キーを文字列(kwSel)からID/正規化キーへ。行データ解決は単一関数、Officeの relatedOf() トークン一致を再利用し二重実装禁止。empty/populated/missing の3状態プレースホルダを先に定義。折りたたみ・選択状態はタブ間独立（1タブ=1目的）。

**Why:** 「通常=見やすさ／Office=詳しさ」の原則を保ったまま通常ビューに詳細配線を足すため。通常側を厚くするとOfficeの存在意義が崩れる。[[detail-explorer-type-a]] のデータ設計（来歴区分・欠損先行定義・単一導出関数）が前提。
**How to apply:** S3/S5パネル化やS2テンプレ化の実装レビュー時にこの線引きと突合する。
